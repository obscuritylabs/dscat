# Native platform resource design

This document owns the macOS-primary resource adapter and independent observation for NFR-001/005 under [DEC-048](decisions.md#dec-048). [Assurance](architecture-assurance.md#resource-enforcement-and-exact-package-matrix) owns existing lexical/archive ceilings; [risk disposition](architecture-disposition.md#native-platform-decision) owns readiness. This is a design candidate, not implemented behavior or product acceptance.

## Threat model and memory contract

Untrusted workbooks, configuration, canonical files and IPC MUST remain data handled by trusted pinned code. Formula/macro/expression execution and network dereferencing MUST remain prohibited. The design MUST preserve finite input/work/retention limits, bounded safe termination, previous outputs and retry. A compromised interpreter/native parser/host and host-wide scheduler/kernel failure remain outside this tool's containment guarantees; process separation MUST NOT be described as a sandbox for arbitrary attacker code.

The macOS adapter MUST combine a fixed finite map-growth limit, the existing finite application limits, independent resident observation and deadlines. It MUST NOT claim a strict 512 MiB resident, footprint or total-allocation ceiling: preexisting mappings can be reused/committed without map growth, resident observation can overshoot, and RSS omits swapped/compressed charges. The prior total 512 MiB address-space metric was an agent design choice, not a direct NFR-005 requirement. Its replacement MUST receive affected architecture/plan review while preserving NFR-005 security acceptance.

## Native adapter and existing topology

Each processing child MUST complete trusted imports, measure its startup virtual bytes, and install hard/soft `RLIMIT_AS` at that frozen measurement plus 512 MiB before reading untrusted request data. It MUST validate native ABI/return/count, checked addition and exact limit readback, and MUST NOT rebase after input acceptance. A new worker MUST establish its own limit after exec. Failure or unavailable enforcement MUST fail closed with `RESOURCE_GUARD_UNAVAILABLE`. This is a hard additional-map-size constraint, not an allocation or physical-memory guarantee. No new absolute startup-virtual ceiling is selected.

The existing nested topology MUST remain: the outer CLI owns the coordinator `Popen`, and the coordinator owns/reaps at most one serial worker `Popen`. The coordinator MUST remain a new session/process-group leader, and workers MUST inherit that group. Trusted code MUST NOT move those processes to another group or create further descendants. Existing typed private request/reply IPC remains bounded at 32 MiB with depth 64; no new control protocol, sole-launch broker, result format, logical heap quota or custom lexical parser is required by this decision.

The outer invocation's main wait loop MUST independently observe the coordinator and its kernel-identified direct worker at a nominal 20 ms cadence. It MUST use `proc_listchildpids(coordinator_pid)` with a fixed small buffer and `proc_pidinfo` task/BSD records; it MUST NOT enumerate unrelated host processes or accept PIDs from untrusted payloads. It MUST verify the owned coordinator's PID, parent, process group and creation time, then verify each candidate worker's parent PID, group and creation identity before and after its resident sample. At most one live worker is permitted. Unexpected descendants, identity mismatch, denied/short native returns or an overflowing enumeration MUST stop the operation. A worker disappearing between samples is an ordinary race: discard its stale sample, re-enumerate, and never signal that numeric worker PID from the outer observer.

Coordinator identity MUST remain anchored by its unreaped direct-child handle. The outer owner MUST detect exit with `waitid(..., WNOWAIT)` while group cleanup is still possible; reader threads MUST report flags rather than reap that coordinator. Only the outer owner MAY reap it after cleanup. All independent observer shutdowns MUST signal the owned coordinator process group, not a potentially reused worker PID. Retaining the unreaped leader prevents its PID/group number from being reassigned during cleanup. The coordinator remains responsible for normal worker termination/reap and independent-file continuation within remaining budgets. If the coordinator has died, the outer owner MUST terminate any remaining group members before reaping its coordinator; already orphaned descendant reaping belongs to the OS adopter, and evidence MUST distinguish this from a successful coordinator `wait` of its own worker.

A resident observation above 512 MiB for either processing child, or an observer failure, MUST trigger whole-operation termination and an operational/resource diagnostic with remaining scope unexamined. This independent emergency stop need not continue subsequent files. Normal per-file timeouts MUST retain coordinator-owned worker kill/reap and continuation. The outer wait loop MUST NOT block on request writes or pipe-reader joins; bounded writer/reader helpers MAY preserve existing IPC without moving watchdog execution into a child thread. Existing 30-second workbook/300-second invocation deadlines and one-second graceful/two-second forced cleanup waits MUST remain. Failure to terminate/reap MUST never be reported as successful cleanup. Scheduling targets are not guarantees during host suspension/kernel failure.

The observer MUST establish native API/identity access to its coordinator before forwarding input. Worker discovery is asynchronous: a newly started short-lived worker can finish between polls. Its own guard and existing input/time limits apply immediately; independent RSS detection is neither instantaneous nor a pre-input acknowledgment for each worker. A child holding its GIL MUST NOT prevent the outer main loop from sampling/stopping its process group. The outer CLI's existing bounded configuration/reply/diagnostic handling remains; it MUST NOT accumulate multiple full replies or retain completed processing children merely to parse them. No new claim that every CLI allocation is independently RSS-contained is made.

Linux MAY retain its verified absolute 512 MiB `RLIMIT_AS` adapter; Windows MAY retain its Job Object process-memory/kill-on-close adapter. Their accounting MUST be reported distinctly. Native macOS installation and the complete workflow MUST pass before first-release acceptance; Windows/Linux remain portability targets and optional further verification MUST gate only claims actually tested on those systems.

## Finite allocation graph and proportional correction

The following source inspection identifies simultaneous allocations and peak cases. These are finite amplification paths under existing ceilings, not evidence of unbounded allocation or justification for a new 128 MiB heap requirement. The native relative-AS guard and independent observer add containment to those existing bounds. Implementation MUST preserve actual byte/count/depth checks before retention at their established boundaries, handle `MemoryError`/native refusal safely, and verify preservation/retry at peak/failure cases.

| Source responsibility | Existing finite source/retention bound and peak case for verification |
| --- | --- |
| `intake.worker.read_source` | Actual workbook at most 32 MiB; mutable read buffer and immutable copy can overlap. Verify overflow/refusal and release after the operation; no claim that only one source representation exists. |
| `intake.archive.read_archive` / `read_member` | At most 4,096 entries, 16 MiB per XML part and 128 MiB actual expansion per workbook; 64 KiB decompression chunks. All retained parts and the current part's mutable/immutable copy may coexist. Their cumulative source is finite; measure the peak and safe refusal rather than invent mandatory spooling. |
| `intake.xml` / `workbook.parse` | XML depth 64, per-part source 16 MiB, at most 200,000 populated cells, individual text 32,767 code points. Expat can materialize attributes/tokens before callbacks, and shared strings/cell/location maps amplify bounded source. Verify giant incomplete tokens, many attributes, repeated shared strings and maximum cells under real adapters. A new lexical pre-parser is not selected. |
| `parse_parts` / `normalize_batch` | Cell maps, row models, detail groups, deduplication/index maps and canonical records overlap; all derive from bounded expanded bytes/cells. Verify conversion peaks and release on workbook completion. No assertion equates serialized bytes to Python heap bytes. |
| `intake.worker` IPC / JSON | Each request/reply at most 32 MiB, depth 64; reader buffer, immutable copy, duplicate-key parse, Pydantic models and serialization can overlap. Validate tiny-node amplification and malformed/duplicate/deep JSON with actual refusal/termination. Pre-Pydantic node admission is not a new obligation. |
| `CandidateRecords` / `validate_catalog` | At most 100,000 datasets and 256 MiB deterministic serialized candidates per invocation; indexes, assessments and sorting/model copies add finite overhead. An individual record serialization occurs before its retained candidate-byte check and can fail; that failure MUST remain bounded by its source and guarded process and preserve prior outputs. |
| Canonical load / save / publication | Individual JSON at most 32 MiB; aggregate generation at most 256 MiB with bounded manifest/file counts. Old catalog, prepared artifact bytes, catalog revalidation and staged reload can overlap. Verify maximum aggregate, many small records, duplication peaks, allocation failure and unchanged CURRENT. Streaming is an optional optimization unless actual evidence establishes a required bounded-failure correction. |
| Outer configuration/result handling | Explicit config/reply inputs remain at most 32 MiB and diagnostics at most 10,000. Copies/parse/render overhead are finite but not identical to wire size. Existing CLI structured validation/privacy/failure tests remain applicable; this design does not impose a new result-rendering protocol. |

The in-progress storage draft was inspected only for these generic lifetime responsibilities; no concurrent source revision or behavior is certified. Retention optimizations MUST remain separate unless a concrete failing safety/acceptance case makes them necessary. The selected requirements promise safe rejection/termination when resource limits prevent processing, not successful materialization of every nominal maximum simultaneously.

## Required evidence and binding tests

Synthetic native probes on 2026-11-19 with CPython 3.15.2 installed hard/soft `RLIMIT_AS = startup + 64 MiB`, read back the exact value, refused a 96 MiB anonymous mapping and accepted/touched an 8 MiB mapping. Startup was 500476133376 bytes, enforced value 500543242240. An own-child `vmmap` summary showed a 385 GiB guard reservation; allocator switches did not make the absolute 512 MiB guard installable. Own-child task info returned 96 bytes. A separate own-process-tree probe returned one kernel-listed child and exact 136-byte BSD records for coordinator/worker, confirming expected parent/group identities and nonzero creation times. `waitid`/`WNOWAIT` are available in this interpreter. These are primitive feasibility observations, not full observer/product acceptance. Exact safe disposable commands MUST accompany external review evidence.

| New decision | Required binding verification before native acceptance |
| --- | --- |
| Startup-relative guard | Actual install/readback before request parsing, refusal using injected small headroom, checked addition/API denial, no rebase, independently initialized worker; reservation reuse explicitly demonstrated with safe small allocations or documented accounting limits. |
| Kernel-scoped nested observation | Actual own-tree enumeration, exact ABI returns, parent/group/creation validation, no unrelated PID accepted, rapid worker creation/exit/replacement, zero/overflow/denied samples and sampling races. |
| Independent cadence and deadlines | Worker/coordinator GIL held, blocked request/response pipe, observer main loop remains active, nominal polling/maximum observed RSS overshoot recorded, real invocation/worker timeout behavior. No zero-overshoot claim. |
| Owned group cleanup | Coordinator exits while worker remains, leader retained with WNOWAIT, group kill before final wait, reader does not reap, normal coordinator worker reap versus OS orphan cleanup distinguished, no reused PID signal, cancellation and clean retry. |
| Existing allocation graph | Peak/hostile cases in each row above, resource failure diagnostics, no partial accepted reply/generation, prior CURRENT/data preservation and successful retry. Unsupported guard/observer MUST fail closed. |

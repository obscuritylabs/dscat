# Local verification and release delivery

## Governing policy and open verification

[Delivery governance](governance.md#local-verification-and-distribution) owns local-first verification, minimal CI, installable private releases and release authority. [Completion stages](governance.md#definition-of-done) and [agent delivery ownership](governance.md#autonomous-delivery-ownership) apply to every task. [NFR-001](requirements.md#nfr-001) owns portability targets and uv installation; actual tested environments MUST be reported. Excel verification arrangements remain deferred under [DEC-028](decisions.md#dec-028), without waiving acceptance. The proposals below MUST NOT be treated as an approved implementation/release plan; current gates are in [planning gates](planning-gates.md).

## Proposed workflow

The following workflow is an LLM proposal and MUST NOT be treated as an approved implementation plan.

- Development SHOULD expose a reproducible local verification command using pinned tools and the committed uv lockfile. The full applicable suite MUST include Ruff checks and formatting, ty, unit/integration/CLI tests, statement/branch coverage, workbook compatibility, hostile-input tests, DCAT-US/ODCS conformance, dependency scanning, and package checks.
- A report MUST identify the exact source commit, dirty-tree state, Python/platform and tool versions, lockfile digest, commands, results, coverage exceptions, vulnerability dispositions, and remaining platform/manual checks. Failed, skipped, or unavailable checks MUST remain explicit. Evidence SHOULD be concise and tracked with the RTM rather than dumping sensitive logs into Git.
- Initial CI SHOULD use one short Linux job on relevant pull-request changes, reusing local commands for fast static checks and a small CLI smoke test once implementation exists. It SHOULD cancel superseded runs and skip irrelevant documentation-only changes. Selected required checks MUST still report a terminal result for every protected PR; path filtering MUST NOT leave a required context permanently pending.
- Broad CI matrices, scheduled full-suite runs, duplicated artifact builds, and automatic release publication SHOULD be omitted. Additional Actions usage MUST require a concrete justification and human agreement. Local platform coverage MUST NOT be claimed without actual evidence.
- Before release preparation, agents MUST verify the task change is merged into origin/main and identify the final main revision. Release preparation SHOULD build a wheel and source distribution locally from that clean, final source revision, test those exact artifacts in a clean environment, inspect proprietary license metadata, and execute the manual verification walkthrough. Release preparation MUST verify supported schemas and offline runtime behavior; dependency installation MAY access PyPI.
- The release candidate SHOULD include wheel, source distribution, SHA-256 checksums, machine-readable SBOM, any justified VEX statements, release notes, workbook compatibility information, and a concise verification report. The manifest MUST bind artifact hashes to the verified source revision. The SBOM MUST describe the distributed artifacts and resolved dependencies.
- Release authorization MUST be explicit before tagging or publication. It MAY be granted during planning for releases meeting agreed scope, version, verification, and security conditions; absent that delegation, human authorization MUST identify the concrete candidate. Agents MUST record the final source revision and hashes and verify they satisfy the authorization. Publication SHOULD upload the already verified artifacts directly from the local environment; it MUST NOT silently rebuild or replace the authorized candidate.
- Private GitHub Release installation instructions SHOULD use authenticated asset download followed by uv tool installation of the downloaded wheel. Documentation MUST distinguish online installation from offline runtime, and MUST NOT embed credentials or assume that private asset URLs are anonymously accessible.
- Post-publication verification MUST download assets from the actual GitHub Release, verify artifact hashes, install in a clean environment, check CLI help/version, and exercise the task-specific acceptance scenarios plus a representative workbook-to-export operation without runtime network access. Documentation changes MUST be verified in the released source archive. A pre-upload local build, draft release, or working checkout MUST NOT substitute for the released version. Remote upload/download verification MUST remain distinct from local candidate checks. Failed post-publication checks MUST be reported and handled under the release failure procedure below once approved.
- Public package-index publication and bundled standalone executables SHOULD remain outside the initial distribution plan unless separately requested. GitHub Releases MUST NOT make this proprietary project public.

## Positive, negative, and failure verification

DEC-033 requires positive and negative tests for all inputs, outputs, and business logic. The verification plan MUST maintain a concise inventory of boundaries and business rules, mapping each to its requirement, success scenarios, failure scenarios, tests, and evidence. Structured and unstructured boundaries MUST be included: CLI arguments, paths and directory discovery, configuration, intake content, canonical storage, diagnostics, serializers, export artifacts, and filesystem publication. This inventory MUST NOT add implementation features beyond approved scope.

- Each boundary and business rule MUST have positive and negative cases. Applicable empty, boundary, malformed, unsupported, conflicting, and hostile cases MUST be exercised; nonapplicability MUST have recorded rationale. Business logic MUST be tested by observable behavior rather than implementation mirroring.
- Output tests MUST verify correct valid results, target schema/semantic conformance where applicable, and safe handling of invalid or unrepresentable results. Serialization and filesystem failures MUST be exercised using controlled failure injection where necessary. Failure checks MUST cover diagnostics, exit behavior, absence of false success, and preservation of existing data and published outputs.
- Verification MUST distinguish expected validation failures from operational failures and MUST record safe termination, recovery/retry behavior where applicable, and residual limitations. Tests MUST NOT execute hostile workbook content.
- Regression fixtures and compatibility checks MUST protect supported submissions, persisted schemas, and public behavior as code evolves. A changed business rule MUST update acceptance criteria and tests through affected change-control gates.
- The manual walkthrough MUST include synthetic positive and negative inputs, exact commands, expected results and failures, preservation checks, recovery steps where applicable, and cleanup. Reports MUST bind evidence to the tested source revision/artifact hashes. Missing tests or unverified failure behavior MUST remain explicit; coverage totals alone MUST NOT establish correctness.

Detailed test design remains pending architecture and implementation planning.

## Draft release evidence and failure policy

The following agent proposals support NFR-005/007/011/012/017. They MUST be approved with the implementation/release plan; they MUST NOT authorize publication.

- The proposed SBOM format is CycloneDX 1.6 JSON. It MUST cover the package and all resolved transitive runtime dependencies of each distributed artifact, with names, versions, package identifiers, provenance, dependency relationships, available license metadata, and artifact SHA-256 bindings. Development/build tools MUST be identified separately rather than misrepresented as installed runtime components. The SBOM generator/version and format validator MUST be pinned and verified under the dependency-age policy before use.
- Dependency sources MUST be PyPI for packages and approved upstream repositories for vendored schemas/contexts; additional indexes, direct URLs, or overrides MUST require recorded provenance/security approval. Frozen synchronization MUST verify the committed lockfile and distribution hashes. Source acquisition and redistribution licenses MUST be reviewed before bundling schemas, contexts, or dependencies.
- Vulnerability evidence MUST identify scanner/version, advisory-source update time, scan time, lockfile/artifact hashes, severity source, findings and disposition. The proposed freshness limit is 24 hours before candidate-specific release authorization and before publication (including exercise of planning-delegated authority); stale or unavailable advisory data MUST block a clean-scan claim and release readiness. Missing severity MUST require explicit assessment, never silent release permission. The approved NFR-012 known-exploitation gate MUST apply independently of severity; evidence MUST assess applicability even for a Low/Medium or unscored finding. High/Critical findings MUST block unless execution-path evidence establishes non-applicability; Medium/Low findings MUST have tracked disposition and revisit conditions.
- A candidate verification failure MUST stop tagging/publication. Agents MUST correct the defect through normal change control, rerun affected checks plus the full release gate, rebuild changed artifacts, and obtain candidate-specific authorization unless an existing explicit delegation covers the new candidate. An unchanged download MAY be retried only after verifying its expected hash.
- A post-publication verification failure MUST keep affected tasks incomplete, identify affected assets/version and whether use is safe, and promptly notify the human. Agents MUST NOT silently replace published assets, reuse a released version for changed content, delete a release/tag, or roll back stored data. A correction MUST follow an approved versioned release or explicitly authorized withdrawal procedure; destructive actions MUST require human authorization. Release notes and verification evidence MUST distinguish the failed release from its correction.
- The exact manual walkthrough MUST be written after command/model design and before candidate-specific release authorization or exercise of explicit planning-delegated authority, using setup, synthetic minimum-core and detailed inputs, canonical reload, each mandatory export, duplicate/conflict and malformed/hostile cases, overwrite refusal/preservation, unsupported versions, retry/recovery, offline execution, installation, and cleanup. It MUST contain actual commands and observed expected results rather than guessed CLI syntax. This document is not that executed walkthrough; the planning-gate table retains the deliverable as PENDING.


## Research revision release dependencies

Approved NFR-020/021/022 require privacy diagnostics/projection verification, selected-application keyboard and assistive-technology checks, an SSDF 1.1 practice mapping, and reporting/remediation/support policy evidence. These MUST be designed against DEC-044 requirements approval and receive architecture/implementation-plan approval before dependent implementation; their checks are not currently implemented or executed. The SBOM proposal above MUST also disclose unknown/missing component fields and reconcile coverage to installed artifact dependencies. A release MUST NOT infer legal applicability, policy enforcement, data access approval, or publication approval from schema validity. No release authority is granted by this revision.

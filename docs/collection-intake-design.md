# Collection intake design

## Scope and authority

This material architecture decision implements the [authorized collection replacement](planning-gates.md#collection-intake-readiness). It owns the changed workbook, canonical evolution and mapping boundaries for FR-001/002/006/007/008/010/011/012/013/014/016 and NFR-005/009/013/020. Other [architecture](architecture.md), [standards](architecture-standards.md) and [assurance](architecture-assurance.md) decisions remain applicable. Product implementation, verification and release evidence are separate. Forecasts, enforcement, discovery and formal lineage implementation are excluded.

## Workbook and typed boundaries

Generated workbook schema MUST be `2.1`, kind `collection-intake`. `Start here` MUST contain visible schema and kind values in D1/D2, bound by single-cell workbook names `dscat_workbook_schema` and `dscat_workbook_kind`; missing, duplicate, moved or conflicting markers MUST fail. The 30-column layout MUST use `Intake`, group headings on row 4, exact unique headers on row 5 and data from row 6. Generation MUST retain existing relative column order and insert `Retention decision authorized by` immediately after retention status. Generated groups, guidance, freeze panes `B6`, dropdowns and table appearance MUST follow INTAKE-024. Generated workbook guidance MUST omit the software license notice; source/package licensing and CLI help MUST retain their existing proprietary notices.

Parsing MUST identify fields by exact header name, independent of physical column order. Workbook `2.0` MUST accept exactly the original 29-header vocabulary. Workbook `2.1` and the bounded input-only alias `2.1-form` MUST accept exactly the 30-header vocabulary, with optional authorizer cell content. The alias MUST normalize to workbook metadata `2.1`; generation MUST NOT emit it. These are closed supported vocabularies, not tolerance for arbitrary version/header combinations. Every vocabulary header MUST occur once; duplicates, missing or unknown nonempty headers and nonempty cells beyond the declared header range MUST fail. Worksheet and table metadata MUST agree in their physical header order after any permutation, and diagnostics MUST report the physical offending column. Fully blank rows MUST be ignored, including styled blank rows; partially populated rows MUST receive ordinary required-field diagnostics. Table range metadata MUST NOT hide entered rows below its range. Parsing MUST inspect all bounded input rows.

The [intake specification](intake-proposals.md#intake-024) owns requiredness and accepted groups. The versioned header vocabulary MUST be materialized in product layout constants from the accepted prototype: collection name/description/location; owner; six sensitivity responses and Other explanation; submitter/date; current amount/unit/basis; consumers/use/access; retention days/status/decision authorizer; process/explanation/source names; per-run amount/unit/basis and typical runs/period. Plain text MUST follow existing NFC/newline/outer-whitespace normalization. Yes/No/Unknown and other controlled choices MUST use exact enum values; Unknown MUST be a state only where explicitly supported. Formulas MUST fail in input cells, irrespective of cached values; strings resembling formulas MUST remain inert text. No new feedback formula column is required.

The existing safe archive -> bounded XML -> located workbook row -> strict typed canonical -> assessment -> storage/export boundaries MUST remain. No general spreadsheet evaluation or `openpyxl` loading of untrusted bytes is authorized. Located messages and diagnostics MUST retain file tokens/sheet/row/field, without placing source paths or raw values in canonical records or normal diagnostics. All new boundary objects MUST forbid unknown fields. The guarded worker/native resource controls and existing fixed limits MUST apply to every new package part and model.

Completion dates MUST accept strict Gregorian YYYY-MM-DD text, OOXML date values with date-only or midnight representation, and finite integral numeric Excel serials using the explicitly parsed workbook `date1904` setting (default false). Numeric conversion MUST occur only for the completion-date field, independently of display format. The 1900 system MUST reject serial 60 (the fictitious leap day) and nonpositive serials; the 1904 system MAY accept serial zero. Fractions, nonmidnight times, booleans, out-of-range dates and unsupported epochs MUST fail with a date correction hint. No locale guessing, current date default or measurement date inference is permitted. Canonical dates MUST serialize as YYYY-MM-DD.

## Identity and absent facts

A collection ID MUST be `collection-` plus the complete lowercase SHA-256 hex digest of the UTF-8 normalized collection name. Normalization MUST use the existing text normalization (NFC, newline normalization, outer whitespace stripping), preserving case and internal whitespace. Identity MUST NOT depend on workbook path, row, owner, submitter or optional metadata. Exact normalized duplicate payloads MUST deduplicate under FR-002; differing payloads with the same ID MUST conflict, with both source tokens reported. Any observed unequal normalized names with equal digests MUST fail as an identity collision. Renaming or changing case/internal whitespace MUST create a different identity; no rename reconciliation or global uniqueness claim is made. Documentation MUST explain this consequence. Existing persisted opaque IDs MUST remain unchanged.

Canonical `1.1` MUST make `description` and `core_party` optional; absence MUST remain omitted, never dummy description text, synthetic contacts or an owner named Unknown. A known owner response MUST populate `core_party` with role `owner` and its supplied label, without invented party IDs, contact association or email. Unknown ownership MUST leave `core_party` absent and record explicit uncertainty in the collection intake object. Existing complete canonical records and all richer metadata groups MUST remain supported. Submitter responsibility MUST remain distinct from ownership and contact facts.

## Collection metadata and quantities

A named OPTIONAL strict `collection_intake` object in canonical `1.1`/`1.2` MUST preserve the following typed fields. Older records MAY lack the entire object; a supplied object MUST contain its required responses. Optional fields MUST be omitted when absent, not stored as null. No untyped extension dictionary is permitted.

| Fields | Encoding and constraints |
| --- | --- |
| `owner_state` | `known` or `unknown`; known MUST agree with supplied owner core party; unknown MUST NOT fabricate one. |
| `sensitivity` | Exactly `pii`, `phi`, `cui`, `pcii`, `isvi`, `other`, each `yes`, `no` or `unknown`; categories independent. |
| `other_explanation` | Optional normalized text; REQUIRED when Other is yes; uncertainty text MAY otherwise be supplied. |
| `submitted_by`, `completed_on` | Required nonempty text and calendar date. Completion is entry review, not data arrival or measurement. |
| `location`, `consumers`, `use`, `access_pattern` | Optional text, with access pattern using the workbook enum. These MUST NOT imply authorization. |
| `current_amount`, `per_run_amount` | Independent optional tagged registration quantities described below. |
| `retention` | Optional status and optional nonnegative integer `days` up to `2^31-1`; trigger fixed to each batch arriving at its destination. Canonical `1.2` MAY additionally carry optional normalized `authorized_by` text. |
| `generation` | Optional process name, explanation, normalized source-name list, optional typical-runs decimal and period enum. No process field is required for collection registration or source-name preservation. |

A registration quantity MUST be absent, `{state: unknown}`, or `{state: known, value: decimal-string, unit: KB|MB|GB|TB|PB, basis: estimate|measured, normalized_bytes: integer}`. Known quantities MUST supply amount/unit/basis; Unknown MUST have blank amount/unit; a wholly blank group MUST remain absent. Units MUST use powers of 1000; `KB` maps numerically to existing canonical `kB` without altering the supplied unit. Existing 28-significant-digit/9-fractional-digit, nonnegative, exact-integral-byte and `2^63-1` bounds MUST apply. Zero MUST remain known zero. No amount MUST be inferred from another collection or run frequency. Workbook numeric cells MUST convert through bounded decimal representations, rejecting booleans/nonfinite values, malformed text and exponent text; canonical decimal serialization MUST be deterministic.

These registration quantities MUST NOT be converted to `KnownCapacity`: Measured reports a submitter's basis, without supplying logical/physical basis, measurement date or observation window. The existing richer capacity observations, binary units and average/peak/window comparisons MUST remain unchanged for persisted catalogs. Typical runs MUST be a nonnegative bounded decimal (the same digit/precision bounds, without byte conversion); numeric runs MUST require day/week/month/year. On demand/Unknown MUST NOT carry a numeric run count. Period alone MAY be supplied. No ingestion rate or forecast MUST be derived.

Retention days MAY be supplied independently of status; a blank status MUST remain absent. `not_yet_determined`, `proposed`, `confirmed` MUST preserve the selected response. Confirmed MUST require days; zero is valid. Optional workbook `Retention decision authorized by` MUST map through lexical `retention_authorized_by` to `RegistrationRetention.authorized_by`. It MUST use existing normalized nonempty bounded text, with blank/whitespace-only input omitted. Attribution alone MUST preserve a retention object without requiring days or status. It MUST NOT imply Confirmed, replace the Confirmed duration requirement, or infer a confirmer, disposal authority, expiry date, legal-hold clearance or storage permission. Registration retention MUST remain separate from existing canonical capacity retention and records-management authorities. Missing confirmation MAY be reported as incomplete metadata but MUST NOT invalidate registration unless Confirmed lacks a duration.

Source names MUST split only on semicolons, trim/normalize each nonempty segment, deduplicate and sort case-sensitively. Optional names MAY remain unresolved, refer outside the workbook or describe several processes; they MUST NOT fail local graph resolution or create synthetic datasets/activities. Name matching MAY inform a nonauthoritative assessment but MUST NOT persist inferred formal edges. These fields MUST NOT emit PROV-O, claim lineage completeness or bypass the later lineage milestone.

## Canonical persistence and compatibility

New collection-intake canonical writes MUST use catalog, canonical manifest and dataset-entry version `1.2` when any registration includes `retention.authorized_by`, and `1.1` otherwise. Existing loaded `1.0`, `1.1` and `1.2` catalogs MUST retain their versions on unchanged save. Canonical `1.2` adds only this optional field to `1.1`; authorizer-free `1.2` catalogs remain valid. The bundle structure, path hashing, locks, generation digest, target fingerprints and atomic CURRENT replacement MUST remain unchanged. Configuration, command/diagnostic JSON, worker protocol and public projection manifest versions MUST remain `1.0` unless their own shape changes; workbook metadata support MUST NOT change unrelated boundaries.

Loaders MUST retain closed strict version-specific decoding: `1.0` requires its original description/core-party facts and forbids `collection_intake`; `1.1` permits the original collection fields but forbids `authorized_by`; `1.2` additionally permits authorizer attribution. Original manifest/record hashes, generation digest and existing target projections MUST be validated against original versioned bytes before returning a version-preserving typed catalog. Loading/saving MUST preserve every existing ID, supported value, richer metadata group and schema version, leaving `collection_intake` absent in old catalogs. It MUST NOT fabricate responses, rewrite old generations or mutate CURRENT. Adding original collection fields to `1.0` MUST require an explicit in-memory upgrade to `1.1`; adding authorizer attribution to `1.0`/`1.1` MUST require an explicit upgrade to `1.2`, before writing a separately authorized destination. Replacement MUST retain old generations under existing rules. No standalone migration command is necessary. Unknown versions, unknown fields, fields forbidden by the declared version, mixed incompatible dataset-entry versions and malformed old records MUST fail. Repeated load/save of unchanged supported data MUST remain byte deterministic.

Software supporting canonical `1.1` cannot read `1.2`; software predating collection intake cannot read `1.1`. This bounded forward incompatibility MUST be documented. Updated software MUST retain genuine `1.0`/`1.1` readability. Workbook `2.0` remains supported alongside `2.1` and the bounded `2.1-form` alias. The undistributed multi-sheet workbook `1.0` remains unsupported; isolated legacy parser fixtures MAY remain regression materials. The public Python API remains unsupported.

## Closed package support

The generated workbook MUST retain one native Excel table and header comments. The current worksheet-only allowlist therefore needs a bounded closure extension, not generic drawing/package support. Support MUST cover only worksheet-local relationship files, table XML, comments XML and the VML note drawing required by ordinary header comments, with explicit path grammars, MIME types and relationship kinds. Generator output MUST normalize its package to this prescribed closure before final validation; absolute or traversal relationship paths MUST NOT be accepted merely because a library emits them.

Worksheet relationship targets MUST resolve to exactly their declared local table/comments/note parts. Relationship IDs, source ownership, reference counts and table/header/range consistency MUST be validated; orphan, missing, multiply owned or type-mismatched parts MUST fail. The generated table name MUST be `IntakeEntries`; its table/header metadata MUST agree with actual headers. Table width and header-note anchor limits MUST remain bounded to the supported 29- or 30-column vocabulary, with AC/AD endpoints selected consistently with that width. Optional note parts MUST bind to header cells only, contain bounded inert comment text and local VML note shapes only. VML MUST use an explicit closed element/attribute grammar for note geometry and cell anchoring: images, hyperlinks, event handlers, scripts, OLE/ActiveX, external references and arbitrary shapes MUST fail. Every XML/VML part MUST pass existing DTD/entity/depth/text/byte/resource checks. No external targets, macros, connections, embedded objects or general drawings are authorized. The precise accepted package vocabulary MUST be materialized with observed generated-package fixtures and hostile mutations before implementation acceptance. Removing comments or flattening the table is not the selected interface.

## Assessment, exports and privacy

Valid minimum registration MUST build/save/load without either export being ready. DCAT required description/contact facts and ODCS required metadata MUST receive explicit missing-fact readiness diagnostics. Every `core_party` dereference, description mapping and public subject binding MUST handle absence before constructing targets; no valid collection row may trigger an internal exception. Existing explicit configuration contact associations MAY satisfy their existing target-specific rules; submitter and owner uncertainty MUST NOT become contacts. Existing complete `1.0` and richer `1.1`/`1.2` catalog exports MUST retain their supported mappings.

New collection metadata MUST survive internal persistence and contribute to mapping-loss reports where omitted by targets. Neither target MUST gain informal schema extensions or formal lineage from this change. New location, submitter, sensitivity, source names, generation text and retention authorizer attribution MUST remain private canonical metadata; they MUST NOT be copied into public projections or broaden the closed publication allowlist. Existing target facts still require their exact subject/value approvals. Sensitivity No MUST NOT grant publication, while Yes/Unknown MUST NOT substitute for a legal determination. Normal diagnostics MUST identify fields and safe correction messages, without printing supplied values. Fixed bundled examples MUST use synthetic metadata and ordinary intake rules, never exemptions.

## Risk and readiness

The decision is moderate risk: new package vocabulary touches an untrusted-input boundary, absence changes existing exporter assumptions, and canonical evolution affects persisted data. The controls above bound those effects through closed grammar, preserved guards, strict versioned decoding, source/version preservation, omission/readiness checks and fail-closed public projection. Name changes create new identities and registration Measured lacks measurement context; these are explicit residual limits, not unresolved design choices. No network capability, irreversible migration, privilege or relaxed external-content acceptance is introduced. Agent architecture disposition: READY for fresh planning; no high-risk decision requiring human approval is identified. Independent affected review MUST cover these security/compatibility decisions before protected integration; this disposition does not claim that review or product acceptance.

Planning MUST bind positive/negative cases for marker/header drift and reordering, all minimum/partial/Unknown combinations, numeric dates/epochs/leap-day rejection, amount/retention constraints, duplicate/conflicting normalized names, unresolved sources, package closure/hostile notes, old detailed bundle integrity and source/version preservation, new save/load determinism, absent-fact target readiness, old rich target outputs, privacy omission and failed output preservation. Ordinary Excel completion/native installed verification MUST use generated `2.1`; another human prototype approval is not required. Both blank/default and fixed seven-row `--examples` generation MUST receive ordinary parser, deterministic-output and overwrite-failure checks. Runtime tests and application observations remain PENDING until executed.

The optional-attribution supplement is moderate risk because it evolves closed persisted vocabulary. Explicit `1.2` versioning, preserved older decoding, private-only attribution and exact per-version headers bound compatibility and disclosure risk; header permutation adds no package vocabulary or executable content. Agent architecture assessment, 2026-11-23: READY for planning under the [authorized supplement](planning-gates.md#retention-attribution-readiness). No high-risk material decision or irreversible migration is introduced. Product and independent review observations remain separate.

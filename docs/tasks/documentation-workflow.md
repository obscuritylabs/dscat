# Documentation workflow maintenance

## Scope and authority

The human instruction dated 2026-11-19 authorizes the proportional workflow remedies and their use while performing this maintenance. This supersedes the universal phase/release and full-review execution rules from the earlier workflow task; its original evidence remains in PR #17 and Git history. This maintenance changes agent execution policy, not product capabilities, security requirements, compatibility promises, or the authority of existing technical decisions.

Included: task classification and stopping conditions; direct implementation for bounded work; focused semantic review and risk-based independence; external nonrecursive review evidence; material-only reopening; separate task/release completion; scope discipline; reconciliation of direct policy dependencies. Excluded: product implementation, unrelated cleanup, usage histories/maps/tracker operations, actual releases, and remote protection/visibility changes.

## Acceptance and verification

- Read-only questions MUST end with an answer, without repository records or SDLC delivery gates.
- Small maintenance MUST use focused checks and requested delivery; it MUST NOT acquire a product release or full-document semantic audit.
- Approved implementation MUST reuse unchanged design decisions. New material requirements/design MUST route affected decisions before dependent implementation.
- Security/privacy/persistence/compatibility and substantive governance changes MUST receive independent review; one reviewer MAY also verify and reconcile the bounded change.
- Factual recording of a pass MUST stop after accuracy and applicable whitespace/link checks; it MUST NOT recursively review its own evidence.
- Optional reviewer suggestions and unrelated defects MUST remain follow-ups. Two failed cycles MUST trigger root-cause analysis or a concrete blocker report, without waiving acceptance.
- Ordinary tasks MUST complete at their requested delivery boundary. Release tasks MUST retain publication and independent downloaded-artifact acceptance, including truthful failures.
- Repository-wide structural checks and whitespace checks MUST pass for this change. One fresh reviewer MUST inspect changed policy and direct dependents for contradictory instructions and retained privacy/security controls.

These scenarios use document inspection; they MUST NOT create synthetic product features, private inputs, tracker publications, or release artifacts. Check results, review disposition, commit identity, and protected integration evidence MUST live in the change PR or external verification record. This record MUST NOT embed its own candidate digest or require a review of factual closure metadata.

## Delivery boundary

This is maintenance with protected remote-main integration as its delivery boundary. No software release is included. Earlier release observations remain historical evidence; current task and release completion are governed by [definition of done](../governance.md#definition-of-done). Completion MUST be reported from actual checks and integration evidence rather than inferred from this plan.

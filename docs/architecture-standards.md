# Proposed standards export architecture

## Status and scope

This is an unapproved architecture proposal supporting [FR-003](requirements.md#fr-003), [FR-004](requirements.md#fr-004), [FR-006](requirements.md#fr-006), [FR-013](requirements.md#fr-013), [FR-014](requirements.md#fr-014), [FR-017](requirements.md#fr-017), [FR-018](requirements.md#fr-018), [NFR-009](requirements.md#nfr-009), [NFR-010](requirements.md#nfr-010), and [NFR-019](requirements.md#nfr-019). Requirements approval is recorded separately in [planning gates](planning-gates.md). Source revision: `697a0764bbdaebd6574079720d3841a8241076a3`; inspected 2026-11-16. Architecture, implementation plan, product implementation, independent verification and release remain PENDING. These research artifacts MUST NOT be installed as a product or treated as an approved compatibility promise.

## Resource identities and offline resolution

The [resource manifest](evidence/architecture/resource-manifest.json) records exact retrieval URLs, SHA-256 byte digests, local files and resolver URIs. The candidate DCAT-US revision is `4996591483b52f4ccc0cb72c42e4ec3fe59a4b06`; ODCS 3.2.0 is `f0bdad95346905d500be5ef4b2c2d9b1d95223b7`. All 26 DCAT-US definition files and the single ODCS schema were directly retrieved. ODCS uses Draft 2019-09 and contains only local fragment references; DCAT-US uses Draft 2020-12 and references other definitions using root-relative paths. Resolver keys MUST use their declared absolute `$id`, rather than infer URLs from filenames or lowercase filenames. The ODCS schema has no `$id`; its immutable retrieval URL MUST be registered explicitly.

The candidate bundle additionally includes 15 published JSON Schema draft/meta-schema documents reached recursively through `$schema`, `$ref`, `$dynamicRef` and `$recursiveRef`. These dated draft URLs are content-pinned by manifest digest; they are not Git revision URLs. All document references and JSON Pointer fragments were audited offline. Vocabulary identifiers name dialect capabilities and MUST NOT trigger HTTP retrieval. Validators MUST support the actual dialects, recursive references and unevaluated-property semantics rather than translate drafts. Unknown reference retrieval MUST fail; a registry callback MUST reject every unbundled URI. Distribution MUST preserve resources byte-for-byte, verify hashes and include them inside installed artifacts.

The exact upstream licenses are bundled: DCAT-US [CC0 dedication](evidence/architecture/resources/dcat-LICENSE.md), ODCS [Apache 2.0](evidence/architecture/resources/odcs-LICENSE), and JSON Schema [upstream license text](evidence/architecture/resources/meta-LICENSE) from revision `4e87b9141e62483383987ddbd27947f1c484b905`. The last contains BSD-style and Academic Free License text; release packaging MUST retain the complete notice and verify applicable attribution before distribution. ODCS pinned tree inspection found no NOTICE file. These third-party notices MUST remain separate from the proprietary application license; no relicense is proposed.

The pinned DCAT-US tree contains no current JSON-LD context resource. The proposed serializer MUST use a finite, inline JSON-LD 1.1 context defining only supported terms; the [minimum fixture](evidence/architecture/minimum-dcat.json) supplies the core context. This has no remote context dependencies. The product MUST NOT use a mutable upstream context, implicit default vocabulary, or arbitrary submitted contexts. Adding supported terms MUST extend and verify the explicit local context; unmapped keys MUST NOT silently disappear during RDF expansion. Product JSON-LD processor pins and installed-artifact validation remain PENDING; the executed architecture-only syntax/expansion and graph experiments are recorded below.

## Minimum core and shared configuration

The experiment separates the [four-field core](evidence/architecture/minimum-core.json), [explicit shared configuration](evidence/architecture/minimum-configuration.json), [DCAT-US output](evidence/architecture/minimum-dcat.json), and [ODCS output](evidence/architecture/minimum-odcs.json). The ID is a dataset identity, not a contract or product identity. Configuration explicitly supplies separate dataset/contract namespaces, catalog IRI, contact email resolution and contract version. Exact permitted target keys MUST be `schema_version = "1.0"`; `identity.dataset_namespace`, `identity.contract_namespace`, `identity.contract_identity_rule = "namespace-plus-dataset-id"`, `identity.parties.<label>.role_email`, `identity.parties.<label>.contact_association`; `dcat_us_3.catalog_id`; and `odcs_3_2.contract_version`. Namespaces/catalog IDs MUST be absolute HTTPS IRIs, end namespaces with `/` or `#`, contain no query/user information/control characters, and remain within the architecture URL policy. Parties MUST be unique normalized labels; email MUST be syntactically valid; contact_association MUST be an actual boolean. Unknown keys MUST fail. Per-record facts and configured values MUST agree when both supplied; disagreement MUST report affected target readiness conflict. The other configuration roots and precedence remain in the [core design](architecture.md#initial-compatibility-contract). No optional intake sheets are used. Shared contact mappings MUST resolve the actual supplied label to a declared contact; a generic fallback contact MUST NOT substitute for an unresolved owner. An owner-only label without an explicit contact association MUST leave DCAT-US unready. Contact resolution MUST NOT infer accountable ownership.

The proposed identity policy MUST concatenate the configured absolute namespace with the percent-encoded UTF-8 dataset ID as one escaped namespace suffix. Contract and dataset namespaces MUST differ; generated identities MUST be collision-checked. Neither application, canonical schema, intake schema nor dataset version MUST supply contract version. A per-record contract identity/version override MAY be supplied and validated independently. Missing contract identity policy/version MUST leave only ODCS unready. Missing DCAT contact email MUST leave only DCAT-US unready. Invalid configuration MUST produce configuration diagnostics before export. This readiness distinction MUST preserve valid minimal intake and MUST NOT establish inventory completeness or publication authority.

| Canonical/configuration value | DCAT-US 3.0 meaning/cardinality | ODCS 3.2.0 meaning/cardinality | Transformation, requiredness and loss |
| --- | --- | --- | --- |
| Dataset ID: one nonempty stable string | `dataset[].identifier`: one string; required by selected Dataset schema | `customProperties` MAY carry `datasetIdentifier`; MUST NOT replace contract `id` | Preserve lexical ID; dataset IRI is separately minted. Dataset identity remains canonical even when omitted from the minimal ODCS fixture. |
| Dataset title: one nonempty string | `title`: one string, required | `name`: one string, required by this mapping though optional upstream | Preserve text; contract name is a metadata label, not evidence of agreement. |
| Dataset description: one nonempty string | `description`: one string, required | `description.customProperties[]`: one `catalogDescription` property/value | ODCS description is an object. A generic dataset summary MUST NOT become an intended-use or purpose assertion. |
| Supplied contact/owner label: one | `contactPoint.fn`: one, with configured `hasEmail`; required contact shape | `team.members[].name`, with explicitly resolved `username`; optional; emit when an explicit contact association resolves | Exact association from configuration; emit no `role: owner` from the core label alone. Unresolved association MUST leave DCAT-US unready; ODCS MUST omit the optional member with an omission diagnostic rather than fabricate identity. |
| Contact email: one configured for label | `contactPoint.hasEmail`: `mailto:` IRI, required | `team.members[].username`: configured address | Validate email/IRI and selected schema pattern; preserve role-based contact preference. |
| Explicit contract namespace or per-record identity | No contract identity substituted into dataset identifier | `id`: one string, required | Distinct contract IRI; deterministic minting under supplied policy. |
| Explicit contract version | No substitution into dataset version | `version`: one string, required | Preserve supplied version; no current-time or tool-version defaults. |
| Serializer constants | `@type: Catalog`, `@type: Dataset`, `@type: Kind`; explicit context | `apiVersion: v3.2.0`, `kind: DataContract` | Standards constants, not invented record facts. ODCS schema also admits older apiVersion values; exporter MUST emit only selected 3.2.0. |
| Catalog identity/dataset namespace | Configured `@id` for catalog and datasets | No catalog identity substitution | Absolute IRIs; dataset membership is `dcat:dataset`. |

The candidate DCAT Catalog schema requires only `dataset`; its Dataset schema requires `description`, `title`, `contactPoint` and `identifier`; Kind requires `fn` and `hasEmail`. The exporter MUST additionally enforce nonempty contact collections and usable values, because upstream permissiveness MUST NOT establish readiness. No access level, publisher, bureau/program code, dates or distribution facts MUST be invented. They are not required by this pinned 3.0 Dataset schema. DCAT-US 1.1 requiredness MUST NOT be imported into the 3.0 exporter.

## Optional mappings and loss matrix

Approval limitation: both first-release targets intentionally omit even explicitly supplied quality/service commitments. FR-004 permits inclusion only when explicitly supplied (a necessary condition, not an obligation to map every supplied assertion); FR-018 permits documented omission with canonical preservation. This proposed boundary MUST be explicitly assessed in the fresh architecture risk assessment and disposition under [governance](governance.md#required-sdlc-and-approval-gates); it MUST NOT imply a waiver, automatic approval or blanket first-release conformance. A future commitment mapping MUST pass affected design/plan gates.

All optional supplied data MUST remain in canonical storage. Every export MUST return a structured omission/loss report keyed by stable record ID, canonical field and target, without echoing sensitive values. Unsupported supplied target content MUST be reported as omitted or target-unready according to representability; an invalid supplied value MUST fail intake validation. Public projection MUST independently enforce [FR-014](requirements.md#fr-014) before target validation. Schema validity MUST NOT imply disclosure approval.

Unresolved optional members and all unmatched role fields MUST be omitted with report; canonical details remain. |
| Dataset modified/date/version | DCAT `modified`: one supplied date string, `version`: one supplied string; ODCS top-level `customProperties[]` named `datasetVersion` with supplied value | Inventory-added and metadata-review dates MUST be omitted with report. Every mapped optional value MUST retain its supplied meaning and cardinality. Repeated references MUST be deduplicated by exact normalized URI; group/member collections MUST use the core deterministic ordering rules. A supplied array/object field type MUST be emitted only as the declared type without invented nested fields. Detailed fixture validation MUST cover the exact supported mapping; additional ODCS types such as map/vector MUST remain named custom properties because they require additional semantics. The finite JSON-LD context MUST additionally define `Distribution`, `distribution`, `accessURL`, `downloadURL`, `modified` with `xsd:date`, and `version`; the [detailed fixture](evidence/architecture/detailed-dcat.json) demonstrates their exact context shapes. Omitted optional facts MUST NOT make otherwise valid minimal exports unready.

The readiness diagnostic cases MUST include `target_contact_missing` for absent explicit association/email (DCAT only), `target_contract_version_missing` and `target_contract_identity_missing` (ODCS only), `target_fact_conflict` for record/config disagreement (affected target), `target_unrepresentable` for an invalid target transformation, and `projection_omitted` for supported canonical information intentionally absent from that target. Missing configuration MUST NOT invalidate four-field intake. Invalid scalar/config shape MUST follow core invocation/configuration failure rules; invalid intake MUST block all targets. Public projection denied MUST remain separate from ordinary target-schema readiness.

## Determinism and validation

Exporters MUST operate on validated canonical records and explicit validated configuration. They MUST sort record collections by stable ID, use fixed ordering for semantically unordered sets, preserve meaningful supplied sequences, emit UTF-8 JSON with fixed indentation/newline policy, and exclude execution timestamps. Version/pin changes MUST be explicit inputs. Scalar RDF literals and object nodes MUST retain intended meaning. Exporters MUST NOT perform network access, execute formulas, dereference references, or invent missing facts. Runtime schema checking MUST use the complete registered closure and package-local bytes. JSON-LD graph tests MUST compare intended named nodes, literals, dataset membership and contact email IRIs rather than merely accept parsable JSON.

The [research verifier](evidence/architecture/verify_resources.py) checks every resource digest, resolves document references and JSON Pointer fragments, and executes positive/negative schema experiments using a network-denying registry. Run it with the temporary research interpreter described in [the execution evidence](evidence/architecture/validation.md). On 2026-11-16, the resource audit passed for 45 resource files, 42 schema/meta-schema documents and 42 referenced document URIs. Both minimum fixtures passed their actual pinned schemas; seven negative mutations per target were rejected. The fixtures were checked against the supplied four-field core/configuration; separate identities and absent invented purpose/service guarantees were asserted. JSON-LD 1.1 expansion and intended catalog/dataset/contact RDF graph assertions passed offline, and unknown schema, malformed context and remote context requests failed. Detailed schema/graph cases are recorded in the same evidence. These are architecture research experiments, not installed-product tests or independent verification. Product dependency pins, complete boundary/business-rule coverage and installed-artifact resource closure remain implementation/verification obligations. No temporary research dependency MUST become a product pin implicitly.

## Later extension boundaries

The release sequence and scope remain authoritative in [requirements](requirements.md#later-capability-acceptance). The first-release architecture MUST preserve independent adapter/readiness interfaces for later W3C DCAT 3, manual PROV-O lineage, ODPS, and DCAT-US 1.1, in that order. Each later capability MUST obtain its own detailed architecture risk assessment/disposition and agent plan readiness; this section MUST NOT select its pins or authorize implementation.

W3C DCAT 3 MUST have its own JSON-LD context/graph tests and dataset/distribution/data-service mappings; DCAT-US conformance MUST NOT imply general W3C export completeness. Manual lineage MUST preserve entity/activity/agent identities and multi-input derivation, use offline JSON-LD and explicitly enumerate supported PROV-O terms; it MUST NOT claim complete PROV conformance or discover external lineage. ODPS 1.1.0 research identifies a candidate, not a selected runtime pin: product identity, lifecycle transition rules, input/output ports, dataset references and ODCS links require a later resource closure and mapping package. The product MUST NOT provision or test endpoints. DCAT-US 1.1 MUST use its own profile, requiredness and compatibility/loss matrix; bureau/program/access facts MUST come from supplied configuration or records, never 3.0 exporter defaults. Canonical records MUST preserve data that any target cannot represent.

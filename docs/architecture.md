# Architecture candidate

This is an agent-proposed architecture against all 42 requirements and the impact package approved at `69b686a3d0b1da49290ca37d577d46fb8b63dbfb` under DEC-044 (2026-11-17). [Planning gates](planning-gates.md) owns approval status. Human architecture and implementation-plan approval remain PENDING. These designs MUST NOT authorize product implementation. The approval package consists of this document, [standards and mappings](architecture-standards.md), [assurance](architecture-assurance.md), [design traceability](rtm.md), and the [revision-specific handoff](tasks/architecture.md). Prior intake/canonical notes MUST serve as navigation to these authoritative detailed proposals, not competing designs.

The approval decision MUST explicitly cover the [first-release supplied-commitment omission limitation](architecture-standards.md#optional-mappings-and-loss-matrix): both initial targets intentionally omit even explicitly supplied quality/service commitments, preserve them canonically and report loss. This proposal MUST NOT be treated as blanket first-release conformance or a human waiver; exact-revision architecture approval remains PENDING.

Version 0.1.0 MUST implement Excel intake, canonical persistence, DCAT-US 3.0, then ODCS 3.2.0, including FR-013–FR-018 and NFR-020–NFR-022. A separate W3C DCAT 3 capability, manual PROV-O lineage, ODPS product/lifecycle/ports, then DCAT-US 1.1 MUST follow in that order. Their reserved boundaries below MUST NOT enlarge the first release. ## Typed boundaries

The proposed package MUST use the following responsibilities, with every named structured message represented by a Pydantic model using strict validation and forbidden unknown fields. Model names specify architectural roles, not an approved public Python API. Internal modules MAY change without compatibility promises. Export and canonical models MUST remain separate.

| Boundary / proposed responsibility | Input model | Output model / failure |
| --- | --- | --- |
| CLI adapter | Parsed command arguments, validated `CommandRequest` | `CommandResult`, `DiagnosticReport`; Typer help/version rendered separately |
| Configuration reader | Bounded TOML bytes, `ExportConfiguration` | Validated configuration and source-key locations; unknown keys fail |
| Discovery | `DiscoveryRequest` | Sorted `SourceDescriptor` sequence and diagnostics; no file content in discovery model |
| Excel adapter | Bounded archive bytes, versioned `WorkbookMetadata`, typed `DatasetRow`, `FieldRow`, `DetailRow` | `IntakeBatch` and source locations; no spreadsheet object crosses adapter boundary |
| Normalization and validation | `IntakeBatch`, shared configuration | `Catalog`, `ValidationAssessment`; no paths in business identities |
| Storage adapter | `CatalogSnapshot`, `Manifest`, `DatasetRecord` | Validated `CatalogSnapshot`; no exporter receives a filesystem path |
| Target projection | `Catalog`, `ExportConfiguration`, target and audience | Dedicated DCAT-US/ODCS boundary models, `ProjectionLoss` and `TargetReadiness`; target-schema validation follows model validation |
| Resource registry | Immutable resource IDs and bytes | Verified local resource handles; unknown IDs fail, no network fallback |
| Publication writer | Fully serialized and validated byte artifacts, `PublicationRequest` | `PublicationReceipt` or operational failure; no partial accepted snapshot |

Raw ZIP/XML/TOML/JSON and command text MUST receive lexical/size checks before model construction; Pydantic alone MUST NOT be claimed to make hostile byte parsing safe. Diagnostic handling, privacy and parser limits MUST follow [assurance](architecture-assurance.md). No SQL/database framework, remote service or runtime network client MUST be introduced for these responsibilities.

## Identity and normalization

Dataset IDs MUST be submitter-supplied opaque text, 1–128 characters after stripping leading/trailing ASCII space and Unicode NFC normalization. Permitted characters MUST be ASCII letters, digits, dot, underscore, colon and hyphen; the first character MUST be alphanumeric. Comparison MUST be case-sensitive; case folding and inferred URL identity MUST NOT occur. Slash, backslash, percent-encoded paths, control characters, dot-only IDs and embedded whitespace MUST fail. A bare ID such as `dataset-017` MUST remain a business identity; target URI encoding MUST use the explicit configured namespace mapping in the standards design. Configuration MUST NOT rewrite IDs before duplicate comparison.

Text MUST normalize Unicode to NFC and CRLF/CR to LF, strip outer whitespace, and preserve internal whitespace and case. Required core text MUST remain nonempty. URLs/references MUST be absolute HTTPS or URN where the individual field permits; role contact email MUST use an explicitly typed email value. URI user information, controls and unsafe schemes MUST fail. URLs MUST NOT be fetched, tested for liveness or normalized by changing path/query semantics. Datetimes MUST require explicit timezone offsets and serialize in UTC with `Z`; dates MUST be strict Gregorian `YYYY-MM-DD`. Booleans MUST accept actual JSON/TOML booleans or workbook controlled `Yes`/`No` only. Numbers MUST NOT accept booleans, nonfinite values, thousands separators or locale-dependent forms.

Rows MUST first normalize and validate into the same canonical model used by saved-catalog loading. Duplicate comparison MUST compare all normalized supported metadata, including explicit Unknown/absent distinctions and independently supplied roles, excluding source locations and workbook feedback cells. Identical IDs and normalized payloads MUST deduplicate, retaining all diagnostic source references outside canonical content. A conflicting payload MUST report both source tokens and block all export. Set-like lists MUST sort by stable normalized keys and reject conflicting duplicate keys; ordered field schemas and process sequences MUST retain explicit order and compare that order. Unchanged content/configuration/tool/resource versions MUST generate identical bytes.

## Canonical record schema

Canonical schema `1.0` MUST be independent of package `0.1.0`, workbook `1.0`, ODCS specification `3.2.0`, supplied contract version, supplied dataset version and any later product version. The initial loader MUST accept only canonical `1.0`; unsupported earlier/future versions MUST fail with `UNSUPPORTED_VERSION` and a separate-destination migration hint. No speculative transforms MUST be implemented. Future migrations MUST be separately approved, version-paired, preserve IDs and supported data, validate a full destination, and leave source bytes untouched. Reapplying a future migration to its target version MUST explicitly refuse or report a documented no-op.

All optional object fields MUST be omitted when not supplied. Explicit Unknown MUST use a tagged state rather than JSON null or the number zero. Null MUST be rejected in schema-defined fields unless a target schema explicitly requires it. The proposed canonical fields and cardinalities MUST be:

| Field group | Typed content and cardinality |
| --- | --- |
| Core | `id`, `title`, `description`: one each; `core_party`: one `PartyReference` with role `contact`, `owner` or `unspecified_contact_or_owner`, label and optional role email/HTTPS reference. A label alone MUST satisfy intake, without inventing accountable roles or export contact facts. |
| Independent identities | OPTIONAL `dataset_version`, `contract_id`, `contract_version`, `product_reference`; opaque supplied strings/typed references. Missing contract identity MAY derive deterministically from a configured contract namespace plus dataset ID only when configuration explicitly declares that identity rule. Product reference MUST NOT imply product completeness. |
| Roles/domain | OPTIONAL lists of `RoleAssignment` (`accountable_owner`, `steward`, `contact`, `maintainer`), each with stable local party ID, role label, optional role email/URI; OPTIONAL domain ID/reference. No contact-to-owner inference. Local party references MUST resolve uniquely; external references MUST be explicitly tagged. |
| Dates | OPTIONAL `inventory_added`, `metadata_reviewed`, `dataset_modified` dates and supplied `update_frequency` text/URI. No substitution among dates; no wall-clock generated timestamp in deterministic catalog content. |
| Distributions/services | OPTIONAL distinct `Distribution` objects with local ID, title, download/access HTTPS URI, media type/format, and `DataService` objects with local ID, endpoint description/URI and explicit served-dataset references. Endpoint descriptions MUST remain metadata, never live checks. |
| Schema | OPTIONAL ordered `FieldDefinition` list, unique `(object_name, field_name)`, supplied type/description, nullable boolean and semantic-reference list. Data samples and defaults containing real data MUST NOT be collected. |
| Consumer detail | OPTIONAL intended uses, limitations, field meanings, access instructions, provenance text, semantic references; OPTIONAL explicit quality/service assertion records. Empty assertions MUST remain absent. Assertions MUST identify subject, kind, supplied value/unit or description and optional source; no monitored-results claim. |
| Governance | OPTIONAL access/use and metadata-disclosure `Determination` objects, publication decision, review evidence, records-management object; exact safe projection behavior MUST follow assurance design. |
| Capacity | OPTIONAL `CapacityObservation` entries and independent capacity retention per the next section. |
| Rules/assessment | OPTIONAL explicitly configured local metadata rule definitions; assessment results MUST remain derived and separate from authoritative records. |

Generic untyped extension dictionaries MUST NOT be accepted in schema `1.0`; unknown intake/canonical fields MUST fail rather than silently disappear. A future schema may introduce a named typed extension only through compatibility review. Standard-specific extra fields MUST NOT flow back into canonical content. All supported fields MUST survive save/load even where no target representation exists.

Records management MUST independently represent disposition authority/reference, trigger text, duration-in-days or supplied instruction, and legal-hold/review states `unknown`, `active`, `inactive` where applicable. Conflicting supplied instructions MUST be retained as explicit conflict entries and produce assessment warnings; incompatible values in one typed scalar MUST fail. No disposal date MUST be calculated and no deletion authority inferred. Determinations MUST retain missing/unknown/partial/full/unrestricted distinctions as defined in assurance; inventory completeness MUST NOT turn them into defaults.

## Intake layout and field encodings

Excel workbook schema `1.0` MUST identify its version in visible `Instructions` cells named `dscat_workbook_schema` and `dscat_workbook_kind` with constants `1.0` and `dataset-intake`. Named cells MUST be validated against their expected coordinates; conflicting/missing markers MUST fail. The initial generated workbook MUST contain Instructions and Datasets; OPTIONAL Fields and Details_Quality MUST be emitted as empty tables with guidance, without requiring completion. Lineage MUST NOT be generated or parsed in 0.1.0. Unknown schema versions or sheets claiming unsupported semantic sections MUST receive actionable errors, not silent partial import. Unrelated sheets without declared intake tables MAY be ignored with a diagnostic; they still MUST pass archive security checks.

Datasets MUST have one dataset per row and required column headers `id`, `title`, `description`, `core_party` and OPTIONAL `core_role`. The four-field conceptual core MUST encode contact/owner using role+party cells as one structured field; a missing `core_role` MUST mean `unspecified_contact_or_owner` and MUST NOT infer accountability or target contact association. The OPTIONAL role dropdown MUST offer contact/owner; leaving it blank MUST NOT invalidate four-field intake. Optional `core_email`, `core_url`, `dataset_version`, dates and independent owner/steward/maintainer columns MAY follow. Rows blank across all input cells MUST be ignored; partially filled rows MUST validate and fail missing core fields. Columns MUST be addressed by unique exact versioned header names, not positional guesses; reordered supported columns MUST work. Duplicate/missing core headers and unknown nonempty headers MUST fail. Blank optional cells MUST mean absent; literal `Unknown` MUST be accepted only in fields with a tagged unknown state. A quoted string `Unknown` in ordinary description MUST remain text.

Fields MUST link by `dataset_id`, with `object_name`, `field_name`, `type`, optional description/nullable/semantic URI. Details_Quality MUST use the seven-column header and grouped property encoding defined in [Optional table vocabulary](#optional-table-vocabulary); repeatable values MUST occupy separate entries. Inline comma-separated lists and arbitrary JSON-in-cell MUST NOT be required. Role, distribution, service, determination, commitment and capacity records MUST use explicit `entry_id`/`property` rows in this table, grouped by `(dataset_id, section, entry_id)` and validated as one typed object. Duplicate property keys MUST fail, even when identical; unordered row order MUST NOT affect results. The closed versioned property vocabulary MUST follow the table below; the implementation plan MUST materialize fixtures for it before parser implementation. Free-form section names MUST NOT bypass validation.

Required cells MUST receive text labels, input messages and missing-value callouts; enums/units/booleans MUST use dropdowns and date/number validation; duplicate IDs MUST receive textual feedback plus highlighting. Feedback formulas MUST live only in designated non-input columns and MUST NOT become imported facts. Cross-file conflicts, schema conformance, reference resolution, authoritative publication decisions and full parser security MUST be reported by CLI validation because worksheet controls cannot establish them. Bypassed workbook controls MUST NOT permit invalid canonical data. Formula-like text MUST remain inert on generation and re-export.

### Optional table vocabulary

`Details_Quality` MUST contain `dataset_id`, `section`, `entry_id`, `property`, `value`, OPTIONAL `unit` and `reference`. Single-value dataset properties MUST use entry ID `dataset`. All values MUST be converted using the property-specific type, not inferred from Excel formatting. Unsupported combinations MUST fail. Repeated reference records MUST use distinct entry IDs, not delimiter parsing.

| Section | Allowed properties; types follow canonical schema and assurance |
| --- | --- |
| `identity` | dataset_version, contract_id, contract_version, product_reference |
| `dates` | inventory_added, metadata_reviewed, dataset_modified, update_frequency |
| `role` | party_id, role, label, email, uri, reference_kind (local/external) |
| `domain` | id, reference |
| `distribution` | id, title, access_url, download_url, media_type, format |
| `service` | id, title, endpoint_url, endpoint_description, served_dataset_id, reference_kind |
| `service_dataset` | service_id, dataset_id, reference_kind |
| `consumer` | intended_use, limitation, access_instruction, provenance, semantic_reference |
| `commitment` | kind (quality/service), subject, description, value, unit, reference |
| `access_determination`, `disclosure_determination` | state, authority, reference, rationale, determined_on, review_status |
| `metadata_review` | state, authority, reference, reviewed_on |
| `publication` | state, authority, approved_on, policy_version, subject_kind, subject_id, target, approved_value_sha256 |
| `records` | authority, reference, trigger, duration_days, instruction, hold_state, review_state, conflict |
| `capacity` | kind (size/average_ingestion/peak_ingestion), state, value, unit, basis, measured_on, window_start, window_end |
| `capacity_retention` | state (unknown/indefinite/known), days |

A repeatable string such as intended uses MUST occupy one unique entry ID per value. Header names MUST be exactly the seven names above; the first five columns MUST be present, and `unit`/`reference` columns MAY be absent. When present, optional cells MUST remain blank unless supported by the property-specific type. A repeated `(dataset_id, section, entry_id, property)` MUST fail even if values agree; inconsistent object identity or conflicting values MUST fail, never overwrite. Group identity MUST use the normalized dataset ID, exact section and normalized opaque entry ID under the dataset-ID grammar. Row ordering MUST NOT change grouped results.

Each `service_dataset` group MUST supply exactly one `service_id`, `dataset_id` and `reference_kind`, with no other properties. `service_id` MUST resolve to exactly one service local ID in the containing record; the grouped `dataset_id` property MUST identify the served dataset in a separate semantic role from the containing row's dataset ID; these IDs MAY be equal. `reference_kind` MUST be `local` or `external`: local values MUST use the dataset-ID grammar and resolve uniquely in the validated catalog; external values MUST be absolute HTTPS or URN references and MUST NOT be dereferenced. Dangling/ambiguous local references, duplicate normalized `(service_id, reference_kind, served dataset)` links across groups and conflicting reference kinds for the same service/reference MUST fail. A service MAY instead supply one `served_dataset_id` plus mandatory `reference_kind` under the same reference rules. This single-link form MUST NOT coexist with any `service_dataset` group for that service, even for a different link; multiple links MUST use only grouped entries. Unsupported service properties MUST fail.

Publication approval entries MUST follow the closed typed subject binding in [assurance](architecture-assurance.md#independent-state-and-public-projection), including exact target, normalized-value hash, policy version and supplied authority/date. Wildcards MUST NOT be accepted. Dataset field schema MUST remain in Fields, not a second competing Details representation. Cells MUST hold one scalar per property; no list/object parsing MUST be inferred.

`assessment.completeness` MUST be a list of explicit canonical field paths, evaluated as present/absent/unknown without modifying the catalog. `assessment.rules` MUST contain unique rule IDs, canonical paths, operator `present`, `equals` or `one_of`, typed scalar operands and OPTIONAL severity `info|warning|error`. Unknown paths/operators, invalid operands and contradictory duplicate IDs MUST fail configuration. Checks MUST be pure local comparisons with results `conforms|does_not_conform|unperformed`; no expressions, imports, scripts, regex execution or organizational enforcement MUST be supported. Rule failures MUST affect declared conformity, not invent universal policy or invalidate otherwise structurally valid intake. Export requiredness MUST remain target-specific and MUST NOT derive from configurable completeness.

## Capacity encoding

A capacity quantity MUST be absent, `{state: unknown}`, or `{state: known, value: decimal-string, unit: ..., basis: logical|physical, measured_on: date}`. For rate observations, `window_start` and `window_end` MUST be timezone-aware timestamps and MUST additionally be supplied for known average/peak ingestion. Decimal strings MUST use digits with optional decimal point (no exponent), at most 28 significant digits and at most 9 fractional digits. Value MUST be nonnegative; exact normalized integer bytes MUST be at most `2^63-1`. Units MUST be `B`, `kB`, `MB`, `GB`, `TB`, `PB`, `KiB`, `MiB`, `GiB`, `TiB`, `PiB`, with decimal factors 1000 and binary factors 1024. Rates MUST use these units per day. Conversion MUST use decimal arithmetic and reject fractional normalized bytes rather than rounding. Original supplied value/unit and normalized bytes MUST both be preserved and consistency-validated on load.

Known values MUST supply basis/date and rate window; unknown MUST NOT invent units/dates. Windows MUST have end after start. Peak MUST be at least average only when basis and both endpoints match. Distinct bases/windows MUST remain incomparable with an informational assessment. Ingestion MUST NOT imply net growth. Retention MUST be absent, unknown, indefinite or known nonnegative integer days (maximum `2^31-1`); calendar months/years MUST fail with a day-based correction hint. Zero MUST remain a known measurement or zero-day retention. No forecast MUST be calculated.

## Storage and deterministic publication

The storage port MUST expose logical `load_snapshot` and `save_snapshot` operations using typed catalog/snapshot values. Exporters MUST receive loaded models only. A user-selected destination MUST be a bundle directory with immutable generations: `generations/<content-sha256>/manifest.json`, `datasets/<sha256-of-normalized-id>.json` relative to that generation, OPTIONAL `exports/`, and one `CURRENT` pointer file at the bundle root. The relative dataset/exports paths in this paragraph MUST be interpreted inside their generation, never as bundle-root siblings. The full dataset hash MUST avoid case/path portability and traversal risks; the manifest MUST map every business ID to its exact expected filename, content SHA-256, schema version and projection resource/configuration fingerprints. Files MUST be UTF-8 JSON, sorted object keys, two-space indentation, LF, no NaN/Infinity, exactly one trailing LF. Dataset order and file entries MUST sort by normalized ID. Decimal source values MUST be strings; normalized bytes MUST be integers. Semantic lists MUST follow the ordering rules above. Fingerprints MUST exclude local source paths and volatile observation times. Canonical filenames MUST NOT reveal raw IDs.

`CURRENT` MUST contain only the full 64-character lower-case generation hash plus LF. It MUST be replaced atomically only after the complete staged generation has been written, flushed, reloaded and validated. Relative paths MUST use the exact prescribed grammar; symlinks, absolute/traversal paths, extra manifest members, missing/hash-mismatched files, duplicate IDs and unknown versions MUST fail. Readers MUST resolve CURRENT once per operation and MUST NOT mix generations. The generation digest MUST cover sorted relative artifact paths plus NUL plus bytes plus NUL, excluding the digest-derived parent name. A changed export selection/configuration MUST form a distinct generation while canonical dataset content remains identical where applicable. Manifest kind MUST be `canonical` or `projection`; a public projection bundle MUST contain only approved derived artifacts and a minimal manifest (kind/version, approved target names, artifact-relative paths and SHA-256 values), never private canonical records, configuration contents, source locations or private loss/assessment reports. Its generation hash MUST cover only those public bytes. Private diagnostics/loss reports MUST require a separate explicitly selected local report destination. The source canonical bundle MUST remain unchanged.

A new bundle MUST be created with exclusive creation. An existing valid bundle MUST require `--replace` even when content is identical; without it the command MUST refuse before writes. Replacement MUST preserve all prior generations and atomically switch CURRENT; it MUST NOT delete omitted records from prior generations. An omitted dataset MUST be absent from the new generation and only that generation. A bundle-root lock file created exclusively MUST serialize writers, including initial creation; stale locks MUST produce a recovery diagnostic and MUST NOT be auto-stolen. A failure before pointer replacement MUST leave prior CURRENT intact. Orphan staged/unreferenced generation directories MUST be ignored by readers and reported for explicit cleanup, never treated as current. No automatic garbage collection MUST remove previous snapshots. Template and diagnostic single-file outputs MUST likewise serialize/validate fully, stage in the destination parent, flush and atomically replace only under explicit replacement authorization; incomplete files MUST NOT become accepted outputs.

Staging and pointer MUST reside on the same local filesystem; cross-device, network/share or filesystems without replace semantics MUST be rejected as unsupported publication destinations. Permission, disk-full, interrupted-write and replace failures MUST fail without reporting success. The guarantee MUST be process-failure atomic visibility, not survival of arbitrary hardware/power loss. Directory/file flush support and atomic replace behavior on actual Windows/macOS/Linux environments MUST be demonstrated before implementation-plan approval; unavailable platform evidence MUST remain a blocker to claiming that environment verified. Storage readers MUST bound file counts/bytes and validate the same schemas as intake, not trust a manifest because it was generated locally.

## Initial compatibility contract

The following proposed public CLI surface MUST be the first compatibility baseline. No public Python API MUST be promised in 0.1.0; imports/internal module symbols MUST be explicitly unsupported. Workbook/canonical schemas and machine-readable diagnostic JSON MUST be versioned independently.

| Command | Required arguments and supported options | Result |
| --- | --- | --- |
| `dscat --help`, `dscat --version` | `--no-color` globally; help MUST include proprietary notice | Help/version on stdout; no catalog I/O |
| `dscat template --output FILE` | OPTIONAL `--replace`, `--diagnostics FILE` | Versioned `.xlsx` intake artifact |
| `dscat validate INPUT` | OPTIONAL `--recursive`, `--config FILE`, `--diagnostics FILE`, `--format text|json` | Assessment only; no catalog outputs |
| `dscat build INPUT --output DIR` | OPTIONAL `--recursive`, `--config FILE`, repeatable `--target dcat-us-3|odcs-3.2`, `--audience internal`, `--replace`, `--diagnostics FILE`, `--format text|json` | Snapshot; no target option MUST mean canonical-only build |
| `dscat export CATALOG --output DIR --target TARGET` | Repeatable mandatory `--target`; OPTIONAL `--config FILE`, `--audience internal|public`, `--replace`, `--diagnostics FILE`, `--format text|json` | Internal snapshot bundle or public projection-only bundle with selected derived outputs; no original workbooks needed |

Audience MUST default to `internal`; `build` MUST persist internal canonical data and reject public audience with an instruction to export from the saved canonical bundle. Only `export` MUST accept `public`, which MUST apply recursive fail-closed projection controls and MUST NOT perform publication/network transfer. `validate` MUST report all target readiness states for the two mandatory targets without treating missing optional export facts as invalid intake. When multiple targets are requested, intake invalidity MUST block every target. Target-specific failure MUST report that target only; an internal bundle MAY publish canonical plus successful requested targets and an explicit failed-target assessment, returning validation exit status, but MUST NOT contain stale/placeholder files for failed targets. A public projection operation MUST withhold its complete projection bundle if any requested public target is blocked; it MUST NOT place private canonical data or diagnostics in that bundle. If no requested target is ready, internal canonical persistence MAY still succeed for valid intake and MUST be explicitly reported; no overall successful-export claim MUST occur. Serialization/write failure MUST abort the whole publication transaction. Previous outputs MUST remain untouched unless an explicit valid replacement reaches the pointer switch.

Exit codes MUST be `0` requested operation succeeded, `1` invalid intake/unready requested target/public projection denied, `2` CLI/configuration/unsupported-version error, `3` I/O/resource/publication failure, `4` unexpected internal failure. SIGINT MUST use `130` with no false success. Multiple errors MUST choose highest-priority failure as internal, operational/resource, invocation/configuration, then validation. JSON stdout MUST contain exactly one versioned `CommandResult`, with sorted diagnostics and summary/assessment/output receipt; ordinary progress MUST be absent in JSON mode. Text stdout MUST promise meaningful labels/counts and textual locations, not exact wrapping/color/prose. Raw input values, absolute paths and stack traces MUST NOT be in normal diagnostics. Stable diagnostic codes, JSON field names and exit behavior MUST have regression fixtures. `--diagnostics` MUST use explicit destination and overwrite protection; report-write failure MUST be operational failure.

Configuration MUST be explicitly passed TOML only; no environment discovery, home-directory search or network configuration MUST affect results. Precedence MUST be command options, explicit config, documented non-factual defaults. Config MUST contain version `1.0`; permitted roots MUST be `schema_version`, `identity`, `dcat_us_3`, `odcs_3_2`, `assessment`, `publication`. Identity MUST hold optional `dataset_namespace`, `contract_namespace`, `contract_identity_rule` (only `namespace-plus-dataset-id`), and `parties` mapping normalized core-party labels to typed `role_email` and explicit `contact_association` boolean. Namespace identity generation MUST require the explicit identity rule. Configured associations MUST NOT infer an owner is a contact. Standards-specific keys MUST follow the mapping document. `assessment` MUST hold explicit completeness criteria and declared local rules; `publication` MUST contain `policy_version` (nonempty string), `allowed_subjects` (unique typed `subject_kind`/`subject_id`/`target` tuples from the closed assurance allowlist) and `authority_reference` (supplied nonempty reference), never inferred approval. Record-level state/authority/date and exact per-value approval scopes MUST remain canonical facts, not be overwritten by policy configuration. Configuration MUST be schema-validated before input processing. Approval scope hashes MUST bind exact normalized canonical, configuration or derived target values under the closed assurance subject model; a hash MUST establish content identity only, not authentic authority. Operators MUST verify supplied authority outside this local descriptive tool; no identity authentication, legal determination or signature service is promised. CLI input/output paths and operational parser limits MUST NOT be overridden through untrusted workbooks/config. Shared metadata MUST fill only explicitly allowed target-required fields; conflicting supplied record/config facts MUST fail affected readiness rather than silently overwrite either source.

Discovery MUST accept regular `.xlsx` files case-insensitively, ignore names starting `~$`, sort by normalized relative path, recurse only with `--recursive`, reject symlinks (including ancestor/destination links), and diagnose unreadable eligible files while continuing independent files. Explicit unsupported files MUST fail rather than disappear. Inputs and outputs MUST be disjoint after normalized resolved-parent checks; output-under-input or input-under-output MUST fail. Empty directories MUST produce an empty valid canonical snapshot, while empty mandatory target catalogs MUST be validated against pinned target constraints and reported unready if necessary. Duplicate physical file selection MUST deduplicate discovery, not import twice.

Compatibility fixtures MUST include generated/current and oldest supported workbook, reordered headers, rejected future versions, minimal/detailed canonical save/load, all state distinctions, identity/version differences, CLI success/failure/JSON/help, config precedence/unknowns/conflicts, omission/replacement, duplicate/conflicting metadata, byte determinism and per-target/public readiness. Only `1.0` intake/canonical/config/report versions MUST initially be supported; no claim MUST imply compatibility with nonexistent older formats. Future minor schema additions MUST preserve old supported input readability, and MUST receive explicit unknown-field/version strategy and migration impact review. Post-1.0 application breaking changes MUST follow the major-version approval policy.

This architecture package MUST receive fresh bounded full-document semantic review and cross-document reconciliation before a ready-for-human-approval claim.

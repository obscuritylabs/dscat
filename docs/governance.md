# Delivery governance

Phase agents MUST read the sections assigned by their [role](workflow.md#phase-routing). The coordinator MUST use the compact control rules in [AGENTS.md](../AGENTS.md) and the [workflow](workflow.md); it MUST NOT load this entire policy merely to route work.

## Authority and statement conventions

- Agents MUST treat approved requirements and planning documents as the source of truth; code MUST conform to them.
- Normative requirements in planning documents and these operating instructions MUST use RFC 2119 keywords (MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, OPTIONAL), interpreted with RFC 8174 uppercase semantics.
- Agents MUST use fact/assumption and provenance markings sparingly, only in planning documents they maintain and where the distinction helps assess a requirement, decision, assumption, or evidence. Agents SHOULD label a shared section or table once rather than repeat markings on every sentence. Requirements MUST retain stable IDs for traceability; ordinary prose MUST NOT receive IDs merely for uniformity. Human-provided or third-party documents MUST NOT be annotated without an explicit request.
- FACT MUST mean a directly supported claim or recorded instruction, not automatic human approval. TOOL_VERIFIED claims MUST cite the source or command, observation date, and evidence. Approval status MUST be recorded separately from provenance.
- Agents MUST NOT imply human approval from silence, elapsed time, tool success, or their own review. Human verification MUST record a date and evidence or decision reference; approver identity MAY be omitted.
- Tables MAY inherit classification from a labeled parent statement when all rows share it. Mixed classifications MUST be labeled per row. Headings, IDs, paths, commands, and literal schema examples MAY omit normative wording when their governing statement supplies it.

- Source code, tests, configuration, package manifests, LICENSE, user-facing documentation, CLI output, and these operating instructions MUST use their conventional formats without planning IDs or fact/provenance annotations. LICENSE MUST use conventional legal prose rather than RFC 2119 formatting. Classification, provenance, and requirements traceability MUST remain in suitable agent-maintained planning documents; agents MUST NOT inject those annotations into ordinary project artifacts.

## Task scope and proportionality

The human-authorized workflow revision dated 2026-11-19 establishes proportional execution for all tasks. Agents MUST select the smallest applicable class and state a concise scope contract: requested outcome, included/excluded work, acceptance checks, and completion condition. A conversational plan or PR description MAY supply it; ordinary tasks MUST NOT require a new planning document, RTM requirement, or phase ledger. Read-only questions need only an answer appropriate to the request.

| Task class | Required work | Delivery boundary |
| --- | --- | --- |
| Read-only advice/review | Inspect relevant evidence and answer; identify limitations | Answer supplied; no repository writes or delivery gates |
| Maintenance | Bounded mechanical/docs/tooling changes or low-risk fixes within approved behavior; focused checks and risk-based review | Requested local artifact or protected integration under the definition of done |
| Approved product implementation | Implement a bounded increment using applicable existing requirements/design; behavior, security, compatibility and integration checks | Verified increment and requested integration; release tracked separately |
| Material decision | New/changed requirements, acceptance, compatibility promise, security boundary, or architecture; affected readiness before dependent implementation | Concrete decision or authorized implementation scope, as requested |
| Release | Explicit release deliverable; full applicable release readiness, publication and independent downloaded-artifact verification | Verified published release |

A task touching several classes MUST apply the controls needed by its actual effects, without expanding its requested outcome. A short edit to a security boundary is still material. Unrelated defects and optional improvements MUST be reported separately; agents MUST NOT silently adopt them as acceptance criteria. Scope expansion MUST identify a concrete dependency or explicit user authorization. The [workflow](workflow.md#failure-reopening-and-shared-state) owns correction limits and stop conditions.

## Required SDLC and approval gates

This section owns approval requests; [planning gates](planning-gates.md) records candidate-specific status. DEC-045 standing delegation remains in force with the proportional workflow revision above. Human approval and agent readiness MUST remain distinct.

- New or materially changed requirements SHOULD require human approval. Agents MAY omit the request when the user explicitly authorized the concrete change or prior explicit approvals entail the only valid solution. They MUST cite that authority and scope; silence, tools, integration, or agent review MUST NOT imply approval. Governance maintenance explicitly requested by the human MAY proceed within that request without a second approval of the same remedies.
- Architecture MAY require human approval only for an agent-assessed high-risk material decision. The agent MUST assess compatibility, privacy, security, irreversible effects, acceptance, and residual risk for that decision; other design readiness MUST remain agent-authorized.
- Requirements, architecture, and plan readiness MUST precede dependent implementation when new material decisions require them, in that order. Existing applicable dispositions MUST be reused. Editorial, provenance, status, or workflow-only changes MUST NOT reopen unchanged product requirements, architecture, or implementation plans solely because their containing file bytes changed.
- Implementation plans and all other SDLC stages MUST NOT require human approval. A fresh planning agent MUST assess material new/revised plans; ordinary increments MAY use a concise plan from their implementer. Applicable independent review MUST follow [review applicability](workflow.md#review-applicability).
- A material unresolved decision MUST block only dependent work and receive concrete analysis and affected phase routing. Routine technical choices within approved boundaries MUST remain autonomous. New suggestions MUST NOT become mandatory deliverables without scope authority.
- Planning, RTM updates, walkthroughs, and evidence MUST be proportional to changed behavior. Product acceptance MUST retain executable positive/negative verification and applicable security/compatibility evidence. Documentation maintenance MAY use policy scenarios and structural checks; read-only answers MUST NOT create SDLC records.
- This delegation MUST NOT authorize repository visibility/protection changes, bypassing protected main, destructive remediation, secrets operations, or unrelated external messages. Privacy, security, licensing, and applicable acceptance constraints MUST remain mandatory.

## Traceability and change control

- Every feature and NFR MUST trace to a capability in docs/rtm.md. Each RTM row MUST link a stable requirement ID to its source, acceptance criteria, design, implementation, tests, and verification evidence.
- Changed product behavior, dependencies, configuration, infrastructure, tooling, migrations, and tests MUST trace to applicable existing requirements. Agents MUST update affected artifact/symbol mappings where behavior changes; line numbers alone MUST NOT be durable identifiers. Governance and documentation maintenance MAY cite the direct instruction and affected policy instead of fabricating product requirement mappings. Unchanged RTM rows MUST NOT be rewritten solely to account for maintenance work.
- Unjustified product behavior MUST receive discrepancy and impact analysis. Agents MUST NOT invent requirements to justify existing code or remove unrelated code during a bounded task. Material correction or removal MUST follow the affected scope decision; unrelated discrepancies MUST remain separate follow-ups.
- RTM fields MAY say PENDING before the corresponding phase; missing implementation or tests MUST NOT be reported as verified. Removed requirements MUST retain a retirement record and impact links; IDs MUST NOT be reused.
- Assumptions affecting correctness, security, interoperability, or acceptance MUST be resolved or dispositioned through the affected requirements/architecture readiness gate before dependent implementation. Exceptions MUST document scope, reason, risk, expiration/revisit condition, and authority under the approval policy above; agents MUST NOT waive required security or acceptance behavior. The human-delegated coverage exception under [engineering constraints](engineering.md#project-and-engineering-constraints) MAY be exercised by agents without additional approval; it MUST NOT waive required behavior or security verification.

## Git, versions, and releases

- Agents MUST use trunk-based development and Conventional Commits. Short-lived feature branches MAY be used and MUST be integrated promptly; long-lived review queues MUST NOT replace trunk integration. Agents MUST create atomic commits frequently, including at least one commit per individual feature and per human interaction producing version-controlled artifacts. A commit MUST NOT combine unrelated work or include unrelated human changes.
- Agents MUST inspect staged diffs for private information, secrets, scope, and traceability before committing. Planning artifacts SHOULD be committed now; future issue migration MUST preserve stable IDs, approval history, and local navigation.
- The initial version MUST be 0.1.0. Pre-1.0 breaking changes MAY occur with documented impacts. From 1.0.0 onward, backward compatibility MUST be preserved within a major version. Breaking major releases MUST be avoided and MUST receive documented compatibility impact analysis and the affected phase readiness dispositions before work requiring them; versioning MUST NOT introduce a separate human approval gate.
- The approved compatibility contract MUST enumerate CLI commands/options, exit codes, structured outputs, configuration, workbook schemas, persisted data, and any public Python API. Breaking changes MUST NOT be hidden in minor or patch releases after 1.0.0.
- Agents MUST use judgment to place durable specifications in files and execution tracking in future issues; agents MUST verify that the configured canonical remote identifies the intended repository without recording its URL. The human explicitly confirmed public visibility on 2026-11-19 and authorized reconciliation of this policy. The repository MAY remain public. Agents MUST NOT change visibility without a new explicit instruction. Public visibility MUST NOT authorize disclosure of private context, sensitive reports or catalog data, relicense the software, waive release checks, or authorize public PyPI publication.

## Local verification and distribution

- Local verification MUST be the primary quality gate. Agents MUST run the applicable lint, formatting, typing, test/coverage, schema interoperability, security, and package installation checks locally and MUST record evidence against the exact source revision and artifact hashes. Reduced GitHub Actions usage MUST NOT reduce verification requirements.
- GitHub Actions MUST remain minimal. Agents SHOULD use at most one small pull-request verification job initially, without broad platform matrices, scheduled full-suite runs, or redundant release builds. Any expansion MUST have a documented need and agent readiness disposition within approved scope. Local commands SHOULD be reusable by the selected CI job.
- GitHub Releases MUST distribute the approved software as installable Python artifacts. Release preparation MUST build and verify a wheel and source distribution locally, include checksums and an SBOM (plus VEX where applicable), and provide download/install instructions appropriate to the authorized repository visibility, including authentication when needed. Required authenticated post-publication verification MUST remain in force.
- DEC-045 supplies standing human delegation for project-scope release preparation, versioning, tags and GitHub Release publication after all applicable scope, verification, security, licensing and artifact-identity checks. Agents MUST record the exact verified main revision, artifact hashes, check results and exercise of this delegation before publishing; no further human approval request is required or permitted for those SDLC stages. Failed checks MUST block publication until corrected and reverified. Passing CI or pushing a tag MUST NOT automatically publish a release. Public PyPI publication MUST NOT be assumed; runtime dependencies MAY be installed from PyPI under the dependency policy.

## Definition of done

Completion MUST match the task class and requested delivery, rather than require every task to ship a release. The scope contract MUST identify a local artifact, remote-main integration, or a release as its delivery boundary. Repository changes SHOULD default to protected remote-main integration unless the user requests local-only work; read-only advice follows its class boundary above.

For repository changes, agents MUST implement the authorized scope, pass applicable focused checks and acceptance verification, resolve blocking findings, update affected documentation/traceability, and inspect the diff for privacy, secrets, scope, and unrelated changes. Integrated delivery MUST additionally use a protected PR/rebase merge and verify the result on remote main. Local-only delivery MUST accurately identify its uncommitted/committed state and MUST NOT imply integration. One reviewer MAY combine independent verification and review where applicable.

Legacy stage numbers remain available for existing evidence: 1 planning/readiness, 2 implementation, 3 tests, 4 local acceptance, 5 remote-main integration, 6 release publication, and 7 downloaded-artifact verification. Stages 1–4 apply proportionally to repository changes; stage 5 applies to integrated delivery. Stages 6–7 belong to a separate release task unless a release is explicitly included in the requested outcome. No task-scoped human waiver is needed for stages that do not apply to its class or delivery. Existing explicit scope exclusions MUST remain respected.

A release task MUST satisfy all applicable release checks, publish verified artifacts under standing delegation, and complete independent verification of the actual downloaded assets in a clean environment. It MUST retain source/artifact identities, checksums, SBOM/security/licensing evidence, installation/offline acceptance, and truthful failure status. A failed release check MUST keep that release task incomplete and block dependent release claims; it MUST NOT reopen an otherwise verified source-maintenance task unless the failure exposes a defect in that task's acceptance.

Evidence MUST identify the tested candidate, applicable checks/results, review disposition, and requested delivery outcome. A PR or external verification record MAY supply it; duplicate task ledgers MUST NOT be required. Release inclusion MAY be linked separately after task completion. Existing PENDING/FAIL release entries MUST remain truthful; this policy MUST NOT retroactively claim a release passed. Factual closure updates MUST follow the [evidence stopping rule](documentation-qa.md#evidence-conventions).

## Autonomous delivery ownership

- Human engagement for approval MUST follow only the requirements and high-risk architecture rules above. Agents MUST own routine implementation, code review, tests, local verification, commits, pushing, PR lifecycle, merging, and delivery evidence within approved scope.
- Plans SHOULD settle acceptance criteria, compatibility, security dispositions, release conditions, and escalation boundaries before implementation. Agents MUST resolve routine technical choices themselves when consistent with that plan and MUST NOT repeatedly request approval for already authorized work.
- Critical PR findings MUST receive concrete impact analysis, correction and routing to the earliest affected phase under the approval policy above. Agents MUST NOT introduce a human PR-review gate; destructive actions or repository-policy changes outside standing delegation retain their separate authorization boundaries.
- Self-review MUST remain candidly identified as agent review and MUST NOT be represented as independent or human review. Agents MUST report results and unresolved gates without handing routine PR work back to the human.
- Merging draft planning documents MUST NOT be represented as approval of their requirements or architecture. Agents MAY integrate requested planning changes autonomously while keeping their approval status explicit.

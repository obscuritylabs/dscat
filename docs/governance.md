# Delivery governance

Phase agents MUST read the sections assigned by their [role](workflow.md#phase-routing). The coordinator MUST use the compact control rules in [AGENTS.md](../AGENTS.md) and the [workflow](workflow.md); it MUST NOT load this entire policy merely to route work.

## Authority and statement conventions

- Agents MUST treat approved requirements and planning documents as the source of truth; code MUST conform to them.
- Normative requirements in planning documents and these operating instructions MUST use RFC 2119 keywords (MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, OPTIONAL), interpreted with RFC 8174 uppercase semantics.
- Agents MUST use fact/assumption and provenance markings sparingly, only in planning documents they maintain and where the distinction helps assess a requirement, decision, assumption, or evidence. Agents SHOULD label a shared section or table once rather than repeat markings on every sentence. Requirements MUST retain stable IDs for traceability; ordinary prose MUST NOT receive IDs merely for uniformity. Human-provided or third-party documents MUST NOT be annotated without an explicit request.
- FACT MUST mean a directly supported claim or recorded instruction, not automatic human approval. TOOL_VERIFIED claims MUST cite the source or command, observation date, and evidence. Approval status MUST be recorded separately from provenance.
- Agents MUST NOT imply human approval from silence, elapsed time, tool success, or their own review. Human verification MUST record a date and evidence or decision reference; approver identity MAY be omitted.
- Tables MAY inherit classification from a labeled parent statement when all rows share it. Mixed classifications MUST be labeled per row. Headings, IDs, paths, commands, and literal schema examples MAY omit normative wording when their governing statement supplies it.

- Source code, tests, configuration, package manifests, LICENSE, user-facing documentation, CLI output, and these operating instructions MUST use their conventional formats without planning IDs or fact/provenance annotations. LICENSE MUST use conventional legal prose rather than RFC 2119 formatting. Classification, provenance, and requirements traceability MUST remain in suitable agent-maintained planning documents; agents MUST NOT inject those annotations into ordinary project artifacts.

## Required SDLC and approval gates

The standing human instruction recorded in [DEC-045](decisions.md#dec-045) governs approval requests. This section is the authoritative approval policy; [planning gates](planning-gates.md) records candidate-specific status. Human approval and agent authorization MUST remain distinct.

- Agents MUST follow startup, fresh-phase routing, requirement traceability, independent verification/review, and all seven completion stages. Each dependent phase MUST wait for the preceding readiness/evidence gate; removing a human approval request MUST NOT waive a deliverable or fabricate readiness. Completion MUST require satisfied acceptance criteria, current documents and RTM, no unresolved blocking defects, and all seven stages below; agents MUST report the actual stage and remaining gates.
- Requirements SHOULD require human approval. Agents MAY omit that request only when prior explicit human approvals entail the only valid solution available. The requirements disposition MUST cite the exact prior approval, revision, date and scope, and explain why no alternative satisfies it. Silence, elapsed time, tool success, document integration and agent review MUST NOT establish the exception or human approval.
- Architecture MAY require human approval only when the architecture agent judges the decision high risk. The agent MUST assess and record concrete scope, compatibility, privacy, security, irreversible effects, acceptance and residual risks against the exact candidate. A high-risk request MUST present the concrete decision package and evidence; otherwise the agent MUST record its own readiness disposition and proceed autonomously when checks pass. An agent disposition MUST NOT be labeled human approval.
- The implementation plan MUST NOT require human approval. A fresh planning agent MUST establish exact ordered increments, acceptance mappings, dependencies, verification, security and release conditions, and record agent readiness before implementation.
- All other SDLC stages, including implementation, verification, review, integration, versioning, release preparation, tagging, publication and post-release verification, MUST NOT require human approval. Agents MUST perform those stages autonomously within project scope after required checks. The standing delegation below supplies release authority; agents MUST NOT introduce another approval request through a routine PR, version choice, risk label or release condition.
- Changes to requirements, architecture, acceptance or plan MUST receive impact analysis and return to the earliest affected phase under this same approval policy. Unresolved material choices MUST block affected readiness, receive concrete analysis and correction or phase routing, and MUST NOT become generic human approval gates outside the requirements and high-risk architecture rules.
- Agents MUST maintain concise planning documents on disk until an explicit migration to GitHub issues, implement small verifiable increments, update RTM/documentation, and provide an executable manual walkthrough with setup, synthetic inputs, commands, expected results, negative cases and cleanup.
- Independent reviews SHOULD occur periodically. Agents MUST record review applicability and use fresh independent reviewers when required; self-review MUST NOT count as independent review. An existing explicit human waiver MAY be honored only within its recorded scope; agents MUST NOT request human review approval or a waiver as a routine stage gate.
- This delegation MUST NOT authorize repository visibility/protection changes, bypassing protected main, destructive remediation, secrets operations or unrelated external messages. Those actions remain outside ordinary SDLC delegation and subject to their separate authority. Privacy, security and acceptance constraints MUST remain mandatory.

## Traceability and change control

- Every feature and NFR MUST trace to a capability in docs/rtm.md. Each RTM row MUST link a stable requirement ID to its source, acceptance criteria, design, implementation, tests, and verification evidence.
- Governance, dependencies, configuration, infrastructure, tooling, documentation, migrations, and tests MUST trace to a supporting capability and requirement. Agents MUST maintain artifact-level mappings and symbol-level mappings where a file spans multiple requirements; line numbers alone MUST NOT be used as durable identifiers.
- Code without an approved RTM justification MUST be removed. Agents MUST first inspect its purpose and dependencies, record the discrepancy and impact, and preserve unrelated human changes. Agents MUST NOT invent a requirement to justify existing code. Removal that changes approved scope MUST pass the affected phase gates under the approval policy above.
- RTM fields MAY say PENDING before the corresponding phase; missing implementation or tests MUST NOT be reported as verified. Removed requirements MUST retain a retirement record and impact links; IDs MUST NOT be reused.
- Assumptions affecting correctness, security, interoperability, or acceptance MUST be resolved or dispositioned through the affected requirements/architecture readiness gate before dependent implementation. Exceptions MUST document scope, reason, risk, expiration/revisit condition, and authority under the approval policy above; agents MUST NOT waive required security or acceptance behavior. The human-delegated coverage exception under [engineering constraints](engineering.md#project-and-engineering-constraints) MAY be exercised by agents without additional approval; it MUST NOT waive required behavior or security verification.

## Git, versions, and releases

- Agents MUST use trunk-based development and Conventional Commits. Short-lived feature branches MAY be used and MUST be integrated promptly; long-lived review queues MUST NOT replace trunk integration. Agents MUST create atomic commits frequently, including at least one commit per individual feature and per human interaction producing version-controlled artifacts. A commit MUST NOT combine unrelated work or include unrelated human changes.
- Agents MUST inspect staged diffs for private information, secrets, scope, and traceability before committing. Planning artifacts SHOULD be committed now; future issue migration MUST preserve stable IDs, approval history, and local navigation.
- The initial version MUST be 0.1.0. Pre-1.0 breaking changes MAY occur with documented impacts. From 1.0.0 onward, backward compatibility MUST be preserved within a major version. Breaking major releases MUST be avoided and MUST receive documented compatibility impact analysis and the affected phase readiness dispositions before work requiring them; versioning MUST NOT introduce a separate human approval gate.
- The approved compatibility contract MUST enumerate CLI commands/options, exit codes, structured outputs, configuration, workbook schemas, persisted data, and any public Python API. Breaking changes MUST NOT be hidden in minor or patch releases after 1.0.0.
- Agents MUST use judgment to place durable specifications in files and execution tracking in future issues; agents MUST verify that the configured canonical remote identifies the intended private repository without recording its URL. Repository visibility MUST remain private unless the human explicitly authorizes a change.

## Local verification and distribution

- Local verification MUST be the primary quality gate. Agents MUST run the applicable lint, formatting, typing, test/coverage, schema interoperability, security, and package installation checks locally and MUST record evidence against the exact source revision and artifact hashes. Reduced GitHub Actions usage MUST NOT reduce verification requirements.
- GitHub Actions MUST remain minimal. Agents SHOULD use at most one small pull-request verification job initially, without broad platform matrices, scheduled full-suite runs, or redundant release builds. Any expansion MUST have a documented need and agent readiness disposition within approved scope. Local commands SHOULD be reusable by the selected CI job.
- GitHub Releases MUST distribute the approved software as installable Python artifacts. Release preparation MUST build and verify a wheel and source distribution locally, include checksums and an SBOM (plus VEX where applicable), and provide authenticated download/install instructions for the private repository.
- DEC-045 supplies standing human delegation for project-scope release preparation, versioning, tags and GitHub Release publication after all applicable scope, verification, security, licensing and artifact-identity checks. Agents MUST record the exact verified main revision, artifact hashes, check results and exercise of this delegation before publishing; no further human approval request is required or permitted for those SDLC stages. Failed checks MUST block publication until corrected and reverified. Passing CI or pushing a tag MUST NOT automatically publish a release. Public PyPI publication MUST NOT be assumed; runtime dependencies MAY be installed from PyPI under the dependency policy.

## Definition of done

Agents MUST NOT mark a task complete, close it as done, or report it as delivered until all seven stages have evidence:

1. The task MUST be planned, mapped to requirements and acceptance criteria, and covered by the applicable requirements/architecture dispositions and agent-authorized implementation plan under the approval policy above.
2. The planned change MUST be implemented, including applicable documentation and traceability updates.
3. Appropriate tests MUST pass and their commands and results MUST be recorded. Documentation-only work MUST receive appropriate document checks; it MUST NOT be silently exempted from the remaining stages.
4. The change MUST be verified locally against acceptance criteria, including relevant integration, security, compatibility, and installation behavior. Evidence MUST identify the tested revision and artifacts; test success alone MUST NOT substitute for acceptance verification.
5. The change MUST be pushed and merged through a pull request into remote main. Agents MUST verify the merged change is present on origin/main; a feature-branch push or local merge MUST NOT satisfy this stage.
6. The change MUST be included in a published GitHub Release from the verified main revision, with the required artifacts and recorded exercise of DEC-045 standing release delegation. A draft release or tag alone MUST NOT satisfy this stage. Multiple tasks MAY share a release, but each MUST remain incomplete until its release and post-release verification are finished.
7. The released version MUST be downloaded from GitHub Releases, its integrity and version MUST be checked, and its applicable acceptance scenarios MUST pass locally using the downloaded artifacts in a clean environment. Software verification MUST install the released package and verify its CLI and offline operation; documentation changes MUST be checked in the released source. Testing the working checkout or a pre-upload build MUST NOT substitute for this stage.

- The task record MUST link planning, implementation/PR, test results, local verification, remote-main revision, release/tag and artifact hashes, and post-release verification evidence. Issues and RTM statuses MUST reflect the actual stage reached.
- Pending applicable requirements/architecture dispositions, readiness evidence, merge, release or post-release verification MUST keep the task incomplete; agents MUST NOT waive a stage or publish a failed candidate merely to claim completion.
- Verification failures MUST keep or return the task to an incomplete state. Agents MUST report the failure, correct it through the same process, and verify the resulting released version before closure.

## Autonomous delivery ownership

- Human engagement for approval MUST follow only the requirements and high-risk architecture rules above. Agents MUST own routine implementation, code review, tests, local verification, commits, pushing, PR lifecycle, merging, and delivery evidence within approved scope.
- Plans SHOULD settle acceptance criteria, compatibility, security dispositions, release conditions, and escalation boundaries before implementation. Agents MUST resolve routine technical choices themselves when consistent with that plan and MUST NOT repeatedly request approval for already authorized work.
- Critical PR findings MUST receive concrete impact analysis, correction and routing to the earliest affected phase under the approval policy above. Agents MUST NOT introduce a human PR-review gate; destructive actions or repository-policy changes outside standing delegation retain their separate authorization boundaries.
- Self-review MUST remain candidly identified as agent review and MUST NOT be represented as independent or human review. Agents MUST report results and unresolved gates without handing routine PR work back to the human.
- Merging draft planning documents MUST NOT be represented as approval of their requirements or architecture. Agents MAY integrate requested planning changes autonomously while keeping their approval status explicit.

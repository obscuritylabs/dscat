# Agent instructions

## Authority and statement conventions

- Agents MUST treat approved requirements and planning documents as the source of truth; code MUST conform to them.
- Normative requirements in planning documents and these operating instructions MUST use RFC 2119 keywords (MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, OPTIONAL), interpreted with RFC 8174 uppercase semantics.
- Agents MUST use fact/assumption and provenance markings sparingly, only in planning documents they maintain and where the distinction helps assess a requirement, decision, assumption, or evidence. Agents SHOULD label a shared section or table once rather than repeat markings on every sentence. Requirements MUST retain stable IDs for traceability; ordinary prose MUST NOT receive IDs merely for uniformity. Human-provided or third-party documents MUST NOT be annotated without an explicit request.
- FACT MUST mean a directly supported claim or recorded instruction, not automatic human approval. TOOL_VERIFIED claims MUST cite the source or command, observation date, and evidence. Approval status MUST be recorded separately from provenance.
- Agents MUST NOT imply human approval from silence, elapsed time, tool success, or their own review. Human verification MUST record a date and evidence or decision reference; approver identity MAY be omitted.
- Tables MAY inherit classification from a labeled parent statement when all rows share it. Mixed classifications MUST be labeled per row. Headings, IDs, paths, commands, and literal schema examples MAY omit normative wording when their governing statement supplies it.
- Agents MUST NOT persist private conversational context, private organizational affiliations, identifying private-context source URLs, or sensitive real-world examples in repository artifacts, Git history, issues, fixtures, or logs. Agents MUST use neutral descriptions and synthetic examples.
- Agents MUST describe the project only through generic product capabilities, technical requirements, and synthetic examples. Agents MUST NOT name, identify, characterize, or imply any customer, agency, intended user or user group, customer-specific use case, operational purpose, deployment context, or reason for adoption. This restriction MUST apply to code, documentation, examples, fixtures, configuration, filenames, commit metadata and messages, branches, issues, pull requests, logs, and release materials. Agents MUST NOT copy private working-directory paths or contextual details from conversations into those surfaces. Public standards and general federal requirements MAY be cited when technically necessary, but MUST NOT be connected to a customer, agency, intended audience, or operational scenario. Agents MUST inspect proposed artifacts and diffs for direct disclosures and identifying combinations of otherwise generic details before committing, pushing, or publishing.

- Source code, tests, configuration, package manifests, LICENSE, user-facing documentation, CLI output, and these operating instructions MUST use their conventional formats without planning IDs or fact/provenance annotations. LICENSE MUST use conventional legal prose rather than RFC 2119 formatting. Classification, provenance, and requirements traceability MUST remain in suitable agent-maintained planning documents; agents MUST NOT inject those annotations into ordinary project artifacts.

## Required SDLC and approval gates

- Agents MUST begin work by reading this file and docs/index.md, checking Git status, and inspecting applicable approved requirements and plans.
- Agents MUST interview the human, record decisions, identify assumptions, and maintain concise on-disk planning documents before implementation. All planning MUST remain on disk until an explicit migration to GitHub issues.
- Agents MUST obtain explicit human approval of requirements, then architecture, then an implementation plan before dependent implementation. Agents MAY prepare clearly labeled drafts before approval. Approval MUST identify the document revision or commit.
- Agents MUST carry approved work autonomously through implementation, self-review, testing, local verification, integration, and authorized release verification; routine implementation and merge decisions MUST NOT wait for human PR review. Changes affecting approved requirements, architecture, acceptance criteria, or plan MUST receive impact analysis and renewed approval for the affected gates before dependent implementation.
- Agents MUST implement in small verifiable increments, update traceability and documentation with each increment, and complete testing before release preparation. Agents MUST NOT request routine human implementation review; any required release authorization SHOULD be settled during planning when the human explicitly authorizes release under stated conditions.
- Agents MUST provide a written manual verification walkthrough with setup, synthetic inputs, exact commands, expected results, negative cases, and cleanup. Human authorization MUST precede release, tagging, publishing, or distribution as a release; an approved plan MAY explicitly provide that authorization under stated release conditions without another implementation review.
- Independent reviews SHOULD occur periodically. The human MAY waive or request agent assistance for an independent review. An agent's self-review MUST NOT be represented as independent review or human approval. Waivers MUST be recorded; review waivers MUST NOT imply release authorization or waived security requirements.
- Completion MUST require every stage in the Definition of done below, satisfied acceptance criteria, current documents and RTM, and no unresolved blocking defects. Agents MUST report the actual stage reached and any remaining gates; a branch push, passing CI, or merge alone MUST NOT be described as completion.

## Mandatory documentation QA/QC

- Every addition, modification, or removal of planning documents or other documentation, including these operating instructions, MUST include a full QA/QC pass before the change is committed, presented for approval, or integrated. Agents MUST review the entire maintained documentation set and applicable operating instructions for consistency and correctness, not only the changed passages. The pass MUST assess completeness appropriate to the current planning stage; missing later-stage deliverables MUST remain explicitly pending rather than be represented as verified.
- The pass MUST check alignment with human instructions and approved baselines; requirements, acceptance criteria, architecture, plans, and traceability; terminology, scope, normative strength, and compatibility; decision supersession and historical versus current instructions; approval scope and revision identification; factual accuracy and supporting evidence; versions, dates, commands, examples, links, and anchors; privacy, security, licensing, and release/completion claims. Technical claims MUST be checked against authoritative sources or reproducible local evidence as applicable. Unavailable evidence MUST be identified as unverified, never assumed correct.
- Agents MUST immediately correct discovered issues across all affected documents within the authorized scope, then repeat the full pass against the resulting document set until no unresolved issues remain except those explicitly deferred by the human. Agents MUST NOT introduce assumptions, fabricate evidence or approval, silently change approved decisions, or bypass approval gates to make documents appear consistent. An issue requiring a human scope, risk, or approval decision MUST be raised promptly with the concrete conflict and a proposed resolution; dependent work MUST wait for that decision while independent authorized corrections continue.
- Human-deferred findings MUST remain unresolved until the human settles them. Agents MUST respect any instruction to discuss findings only in conversation and MUST NOT persist those findings without authorization. A deferral MUST NOT excuse a new inconsistency or an expansion of an existing issue. Agents MUST report the checks performed, evidence limitations, and unresolved human-deferred issues accurately; a QA/QC pass MUST NOT be represented as independent review, human approval, or proof that future defects are impossible.
- Agents MUST follow docs/documentation-qa.md for each documentation change, reconcile authoritative statements and dependent summaries in the same increment, and use docs/planning-gates.md for consolidated approval status. Requirement links MUST target stable anchors; structural checks MUST verify links/anchors, unique identifiers, complete RTM membership, and valid decision/capability references. Semantic review MUST explicitly check supersession, approval scope, evidence reproducibility, and current-versus-historical instructions. Agents MUST NOT treat structural-check success as semantic correctness or a guarantee against future defects.

## Traceability and change control

- Every feature and NFR MUST trace to a capability in docs/rtm.md. Each RTM row MUST link a stable requirement ID to its source, acceptance criteria, design, implementation, tests, and verification evidence.
- Governance, dependencies, configuration, infrastructure, tooling, documentation, migrations, and tests MUST trace to a supporting capability and requirement. Agents MUST maintain artifact-level mappings and symbol-level mappings where a file spans multiple requirements; line numbers alone MUST NOT be used as durable identifiers.
- Code without an approved RTM justification MUST be removed. Agents MUST first inspect its purpose and dependencies, record the discrepancy and impact, and preserve unrelated human changes. Agents MUST NOT invent a requirement to justify existing code. Removal that changes approved scope MUST pass the affected approval gates.
- RTM fields MAY say PENDING before the corresponding phase; missing implementation or tests MUST NOT be reported as verified. Removed requirements MUST retain a retirement record and impact links; IDs MUST NOT be reused.
- Assumptions affecting correctness, security, interoperability, or acceptance MUST be resolved or explicitly accepted by the human before dependent implementation. Exceptions MUST document scope, reason, risk, expiration/revisit condition, and authorization. The human-delegated coverage exception under Project and engineering constraints MAY be exercised by agents without additional approval; it MUST NOT waive required behavior or security verification.

## Project and engineering constraints

- DSCat (Dataset Catalog) MUST be a uv-managed Python package with a Typer CLI. All structured boundary input and output MUST pass through Pydantic models, including workbook records, exports, configuration, and structured diagnostics. Ordinary CLI help and human-readable rendering MAY be derived from those models.
- DSCat MUST generate Excel workbooks for human completion, validate returned workbooks, and export validated catalog metadata to DCAT-US. The initial release MUST export DCAT-US 3.0 and ODCS; DCAT-US 1.1 SHOULD be supported without blocking release. Exact ODCS version and minimal conforming scope MUST be approved before implementation.
- Any RDF export MUST use JSON-LD serialization. Its contexts and validation resources MUST support offline operation; canonical catalog JSON MUST NOT be conflated with an RDF serialization.
- The project MUST select the latest stable Python at initial implementation and MUST verify dependency/tool compatibility. Agents MUST report incompatibility rather than silently downgrade. Python upgrades thereafter MUST receive impact analysis.
- uv MUST exclude dependency artifacts uploaded less than 14 days before resolution, including development dependencies. The implementation SHOULD use exclude-newer = "14 days" after verifying support in the pinned uv release. Lockfiles MUST be committed and routine verification MUST use frozen synchronization. The age policy MUST NOT be treated as vulnerability protection by itself.
- Ruff MUST enable ALL rules and formatting checks. ty MUST enable all available diagnostics at error severity. Agents MUST verify current configuration syntax and tool support. Mutually exclusive rules and formatter conflicts MUST receive narrow documented resolutions; blanket ignores, diagnostic baselines, and unchecked typing escapes MUST NOT conceal defects.
- All maintained Python code MUST be typed and compliant with the configured checks. The verification plan MUST target 100% statement and branch coverage and behavior-based acceptance tests. Agents MAY make narrow coverage exceptions with recorded rationale, scope, risk, and compensating verification; coverage alone MUST NOT establish correctness.
- Security MUST be a hard requirement. Agents MUST plan and verify dependency vulnerability checks, lock integrity, approved package sources, secret exclusion, safe workbook parsing, and safe output generation. Agents MUST NOT execute workbook macros, formulas, external links, or untrusted content. Generated workbooks MUST use normal Excel validation features and formulas where practical, without macros or executable code. Excel MAY evaluate these formulas; DSCat MUST independently validate returned data without executing formulas or trusting cached formula results.
- Tests MUST include positive and negative cases for every structured and unstructured input/output boundary and every business rule, including ordinary business logic. Verification MUST establish where and how operations fail, actionable diagnostics and exit behavior, preservation of existing data and outputs, and successful recovery or retry where applicable. Boundary, empty, malformed, unsupported, conflicting, and hostile cases MUST be covered where applicable; nonapplicability MUST be documented. Output verification MUST cover valid results and rejection or safe handling of invalid or unrepresentable results, serialization errors, and write failures. Compatibility and regression tests MUST protect supported behavior as schemas and business logic evolve. Coverage percentages MUST NOT substitute for this behavior-based evidence.
- Tests MUST cover malformed and hostile inputs, validation failures, interoperability with pinned external schemas, and failure without corrupting outputs. External schemas and dependencies MUST have recorded versions and provenance. Unknown vulnerability status MUST NOT be reported as a clean scan.
- Accessibility and performance MAY remain without dedicated targets unless a requirement or security constraint warrants them.

## Git, versions, and releases

- Agents MUST use trunk-based development and Conventional Commits. Short-lived feature branches MAY be used and MUST be integrated promptly; long-lived review queues MUST NOT replace trunk integration. Agents MUST create atomic commits frequently, including at least one commit per individual feature and per human interaction producing version-controlled artifacts. A commit MUST NOT combine unrelated work or include unrelated human changes.
- Agents MUST inspect staged diffs for private information, secrets, scope, and traceability before committing. Planning artifacts SHOULD be committed now; future issue migration MUST preserve stable IDs, approval history, and local navigation.
- The initial version MUST be 0.1.0. Pre-1.0 breaking changes MAY occur with documented impacts. From 1.0.0 onward, backward compatibility MUST be preserved within a major version. Breaking major releases MUST be avoided and MUST receive explicit human approval before work requiring them.
- The approved compatibility contract MUST enumerate CLI commands/options, exit codes, structured outputs, configuration, workbook schemas, persisted data, and any public Python API. Breaking changes MUST NOT be hidden in minor or patch releases after 1.0.0.
- Agents MUST use judgment to place durable specifications in files and execution tracking in future issues; origin MUST be https://github.com/obscuritylabs/dscat. Repository visibility MUST remain private unless the human explicitly authorizes a change.

## Catalog behavior and licensing

- Intake capabilities MUST remain technology-neutral where practical. Excel SHOULD be the initial intake technology; workbook-specific obligations in these instructions and planning documents MUST apply only while Excel is selected. A replacement decision MUST revise or retire technology-specific requirements and acceptance criteria through affected planning approvals, preserve applicable intake capabilities, and address compatibility. Workbook-specific MUST clauses MUST NOT make Excel selection mandatory.

- Workbooks MUST be intake artifacts; a Pydantic-backed canonical JSON catalog MUST be the persisted source of truth, with DCAT-US and ODCS derived from it. Canonical data MUST be kept in organized flat files for now. The architecture MUST treat the canonical schema as a migration boundary and keep persistence separate from the catalog model to allow a future database adapter without coupling exporters to file paths. DSCat MUST accept individual workbooks or a directory and MUST rebuild deterministically and idempotently from unchanged inputs without requiring an application database.
- Validation MUST examine all readable inputs and collect all discoverable failures before returning failure; catalog exports MUST be blocked by default on any failure. Fatal unreadable files MUST be reported while validation continues on other inputs; agents MUST NOT claim to validate unreadable content.
- Workbooks MUST prioritize participation through a small required core and optional detail fields. Capacity metadata MUST support current size, average and peak daily ingestion, retention, and measurement date, with explicit Unknown allowed. Unknown MUST NOT become zero. Version 0.1.0 MUST NOT implement forecasts.
- Installed runtime operations MUST work offline. Network-dependent dependency/security checks MAY run during development or release preparation; authoritative schema validation MUST NOT require runtime downloads.
- Releases MUST include a dependency SBOM. Known High or Critical vulnerabilities MUST block release unless evidence establishes non-applicability; VEX MAY document non-applicability supported by execution-path analysis. Severity assessment, affected artifacts, and supporting evidence MUST be recorded; scanner absence or missing severity MUST NOT silently establish safety.
- Workbook schema compatibility MUST be explicitly versioned, tested, and tracked as the principal compatibility surface.
- The project MUST be proprietary to Obscurity Labs. LICENSE and Python project metadata MUST express the proprietary license and CLI help MUST display a matching notice. Agents MUST NOT substitute an open-source license or publish proprietary artifacts without release authorization.

## Main branch protection

- Agents MUST follow the active ruleset documented in docs/repository-policy.md. The human deleted local/github/main.ruleset.json after activation; agents MUST NOT recreate it without a new request and MUST keep the path excluded from Git. Remote protection changes MUST require explicit human instructions.
- The currently active protection requires pull requests with resolved conversations and rebase merges into main. Agents MUST create, review, and merge those PRs themselves once applicable checks pass; human review MUST NOT be a routine merge gate. This PR mechanism MUST be recorded as an agent-selected protection choice, not a human requirement for trunk-based development. Agents MUST NOT directly push, force-push, delete, or bypass protections on main. The one-time bootstrap has been consumed and MUST NOT be used again.
- Required GitHub approval count MUST be zero in the single-contributor workflow; human planning and release approval gates MUST remain mandatory. Full applicable local verification MUST be run and recorded before merge. Any configured minimal CI checks MUST also pass; required-check rules MUST be limited to the selected small CI workflow once stable check names exist.

- Identical dataset records sharing an ID MUST deduplicate; conflicting records sharing an ID MUST block export with both source locations. Neither duplicate handling nor canonical storage work MUST bypass complete validation or the remaining human architecture/planning gates.

## Local verification and distribution

- Local verification MUST be the primary quality gate. Agents MUST run the applicable lint, formatting, typing, test/coverage, schema interoperability, security, and package installation checks locally and MUST record evidence against the exact source revision and artifact hashes. Reduced GitHub Actions usage MUST NOT reduce verification requirements.
- GitHub Actions MUST remain minimal. Agents SHOULD use at most one small pull-request verification job initially, without broad platform matrices, scheduled full-suite runs, or redundant release builds. Any expansion MUST have a documented need and human agreement. Local commands SHOULD be reusable by the selected CI job.
- GitHub Releases MUST distribute the approved software as installable Python artifacts. Release preparation MUST build and verify a wheel and source distribution locally, include checksums and an SBOM (plus VEX where applicable), and provide authenticated download/install instructions for the private repository.
- Agents MUST establish human release authorization before creating a release tag or publishing assets. Authorization MAY be explicitly delegated during planning for releases meeting agreed scope, verification, security, and versioning conditions; otherwise the existing human release gate MUST remain. Agents MUST verify the actual candidate meets the authorized conditions and MUST NOT infer release permission from silence or ordinary plan approval alone. Passing CI or pushing a tag MUST NOT automatically publish a release. Public PyPI publication MUST NOT be assumed; runtime dependencies MAY be installed from PyPI under the approved dependency policy.

## Definition of done

Agents MUST NOT mark a task complete, close it as done, or report it as delivered until all seven stages have evidence:

1. The task MUST be planned, mapped to requirements and acceptance criteria, and covered by the required human approvals.
2. The planned change MUST be implemented, including applicable documentation and traceability updates.
3. Appropriate tests MUST pass and their commands and results MUST be recorded. Documentation-only work MUST receive appropriate document checks; it MUST NOT be silently exempted from the remaining stages.
4. The change MUST be verified locally against acceptance criteria, including relevant integration, security, compatibility, and installation behavior. Evidence MUST identify the tested revision and artifacts; test success alone MUST NOT substitute for acceptance verification.
5. The change MUST be pushed and merged through a pull request into remote main. Agents MUST verify the merged change is present on origin/main; a feature-branch push or local merge MUST NOT satisfy this stage.
6. The change MUST be included in a published GitHub Release from the verified main revision, with the required artifacts and explicit human release authorization. A draft release or tag alone MUST NOT satisfy this stage. Multiple tasks MAY share a release, but each MUST remain incomplete until its release and post-release verification are finished.
7. The released version MUST be downloaded from GitHub Releases, its integrity and version MUST be checked, and its applicable acceptance scenarios MUST pass locally using the downloaded artifacts in a clean environment. Software verification MUST install the released package and verify its CLI and offline operation; documentation changes MUST be checked in the released source. Testing the working checkout or a pre-upload build MUST NOT substitute for this stage.

- The task record MUST link planning, implementation/PR, test results, local verification, remote-main revision, release/tag and artifact hashes, and post-release verification evidence. Issues and RTM statuses MUST reflect the actual stage reached.
- Existing human approval gates MUST remain mandatory. Pending approval, merge, release, or post-release verification MUST keep the task incomplete; agents MUST NOT waive a stage or publish without authorization merely to claim completion.
- Verification failures MUST keep or return the task to an incomplete state. Agents MUST report the failure, correct it through the same process, and verify the resulting released version before closure.

## Autonomous delivery ownership

- The human MUST be engaged for requirements, architecture, planning decisions, and unresolved scope or risk decisions. Agents MUST own routine implementation, code review, tests, local verification, commits, pushing, PR lifecycle, merging, and delivery evidence within approved scope.
- Plans SHOULD settle acceptance criteria, compatibility, security dispositions, release conditions, and escalation boundaries before implementation. Agents MUST resolve routine technical choices themselves when consistent with that plan and MUST NOT repeatedly request approval for already authorized work.
- Agents MAY request human review of a critical PR when it exposes an unresolved material decision, such as an unapproved compatibility break, destructive migration, security exception, or change to approved scope. Criticality MUST NOT automatically create a human code-review gate when the decision is already covered by the plan. Escalation MUST identify the precise decision needed, with the concrete change and evidence prepared for review.
- Self-review MUST remain candidly identified as agent review and MUST NOT be represented as independent or human review. Agents MUST report results and unresolved gates without handing routine PR work back to the human.
- Merging draft planning documents MUST NOT be represented as approval of their requirements or architecture. Agents MAY integrate requested planning changes autonomously while keeping their approval status explicit.
